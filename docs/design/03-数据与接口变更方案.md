## 0. 一页结论（TL;DR）

### 0.1 「要改多少」的直接回答

- **数据库**：现有 28 张表，**10 张完全不动**、**12 张加列/改列**、**5 张只加唯一键或索引**、**0 张新增**、**1 张废弃**；另有 **8 张「无实体类」的表**——**2026-11-01 实测：8 张全部真实存在**（`region` 3231 / `permission` 31 / `system` 18 / `keyword` 7 / `issue` 4 / `role` 3 / `groupon` 0 / `notice_admin` 0 行），逐张处置见 §4.6；它们**存在但无实体、无需求归属 ⇒ 不作需求载体**，故不进 28 张的保留/废弃分母。
- **接口**：现有 124 个端点（对外 84 + 内部 `/inner/**` 40），**84 个保留不动**、**36 个改契约**、**4 个废弃**（84+36+4=124）；另需**新增 37 个对外端点**（R1 21 / R2 **15** / R3 1）**+ 32 个对内端点**（**28 个转发** + 4 个服务间专用，见 §5.3.1）。
- **列级**：新增列 **35 条**（若选「显式锁量」则 36 条）、废弃列 **7 条**、新增唯一键/索引 **18 个定义 / 17 个净增**（唯一键 8 + 普通索引定义 10、**实际净增 9**；`idx_og_order` 建后即删）。
- **一句话**：**表结构是"加法为主、几乎不拆表"**——多规格、按行售后、超时关单、库存视图、报表五件事都能落在**现有 28 张表的加列 + 派生查询**上；真正的大头在**接口层**（售后状态机整族接口缺失）与**实现层**（金额口径、锁量语义、状态字典）。

### 0.2 六个头条结论（每条都指向一份证据）

1. **多规格 SKU 不需要新表**。`litemall_goods_specification` 已是「维度-值字典」（`goodsId/specification/value/picUrl`，`GoodsSpecification.java:34/37/40/43`），`litemall_goods_product` 已是「组合行」（`specifications` JSON + `price` + `number`，`GoodsProduct.java:38/41/44`）。缺的是**稳定标识**与**组合唯一性**：加 `sku_code`、`spec_value_ids` 两列 + 2 个唯一键即可满足 `BR-GOODS-02`（`:140`）与 `BR-GOODS-07`（`:145`）。
2. **按行售后不需要新表**。`BR-AS-01`（`需求文档.md:293`）规定「一次申请只针对 1 个订单行」⇒ 售后单与订单行是 **1:1**，给 `litemall_aftersale` 加 `order_goods_id + number` 即可；建子表是为未来预留的空转抽象（详见 §4.1 方案 M-3）。
3. **锁量可以零结构改动**。原型已用派生法跑通 13 步验收：`lockedQty(sku) = Σ 未付款订单该 SKU 数量`（`prototype/assets/store.js:451-459`）、`sellable = number − lockedQty`（`:467-471`）、**下单不扣 `number`**、支付成功才一次性实扣（`store.js:744-747`）。代价从"加一列+回填+防不一致"降为"一次聚合查询 + 行锁/条件更新"（§4.1 方案 M-2）。
4. **金额单位是横切开关，必须先定，不能边做边定**。库内 16 个有效金额列全是 `BigDecimal` 元（`01` §2.5；`PayServiceImpl.java:121` 仅在支付边界 `movePointRight(2)`），需求 7.2 要「分」（`需求文档.md:528`）。选「库内改分」要动 16 列 9 张表；选「边界换算」动 0 列但要求全链路纪律（§4.7）。
5. **最大的缺口不在表，在接口**。售后模块现状**只有 1 个端点**（`POST /app/aftersale/apply`，`AftersaleController.java:25`），需求要 8 态状态机 + 后台处理台（`BR-AS-06~23`，`:299-317`）；后台**无任何售后查询/审核接口**（`02` §6.2）。本方案新增的 37 个端点里 **13 个是售后**。

## 4. 数据库变更方案

> 全部为**草案**。施工前必须由 DBA 提供线上 `SHOW CREATE TABLE`（`01` I-01），据此校正列长度/精度/字符集/既有索引；本文的列类型按 `db-migration-M10-bigint.sql` 的目标态（ID 为 `BIGINT`）与 `01` §3.2 的 Java 类型推定。

### 4.1 三个必须先定的方案（A/B 并列，不做取舍）

> ✅ **用户已确认（2026-11-01）**：M-1 = ②（详见 §4.7）、M-2 = **A 派生锁量**、M-3 = **① 加 2 列**、M-4 = **① 落 `merchant_id`（+2 列）**。下方 A/B 并列与代价说明保留供追溯，**不再作为待选项**。

#### M-2 锁量：派生 vs 显式列

| 维度 | **A · 派生锁量（本文量化基准）** | **B · 显式锁量列** |
|---|---|---|
| 表结构 | **0 列** | `goods_product` +`locked_number INT`（1 列） |
| 可售定义 | `sellable = number − Σ(未付款订单该 SKU 数量)`，与原型 `store.js:467-471` 完全一致 | `sellable = number − locked_number` |
| 下单动作 | **不写库存**：只落订单行（`order_goods.number`），锁量随订单状态存在而存在 | 写 `locked_number += n`（条件更新 `WHERE number − locked_number >= n`） |
| 支付成功 | 一次性 `UPDATE ... SET number = number − n WHERE id=? AND number >= n`（**只此一次实扣**） | `locked_number −= n` 同时 `number −= n`（两列一次改） |
| 关单/取消释放 | **无需任何库存写操作**（订单状态一变，派生锁量自动消失） | `locked_number −= n`（必须成功，否则锁永久泄漏） |
| 并发正确性 | 依赖对同 SKU 行的**行锁**（`SELECT ... FOR UPDATE` 汇总未付款占用 + 校验）或「先插入订单行、再在事务内做一次汇总校验」；也可用「`number` 条件更新兜底」 | 依赖 `UPDATE ... WHERE number − locked_number >= n` 的**原子条件更新**（单语句天然串行化） |
| 超卖防线（**必须写清**） | A 的**唯一兜底**在支付成功那一次 `UPDATE ... SET number = number − n WHERE id=? AND number >= n`：若返回 0 行，说明期间发生了并发超卖，此时整单纯失败并回滚（不置已支付），提示"库存不足"。**下单侧的汇总校验不是防线**（它只是"尽力而为的早失败"），因为两个并发请求可能都通过校验 | B 的防线是下单时的条件更新（`locked_number` 原子增），失败即整单失败（`BR-ORDER-04` `:216`） |
| 风险 | ① 每次下单多一次聚合查询（可用索引缓解）；② 报表/库存视图需现算，不能直读一列 | ① 双写一致性；② 存量回填；③ 任何漏释放的路径都会造成"锁泄漏"（比超卖更难发现） |
| 迁移 | **无** | 回填 `locked_number = Σ(未付款订单该 SKU 数量)` |
| 原型是否已验证 | **是**：`store.js:451-459 / 467-471 / 744-747 / 759-777`，13 步验收实测（`README.md:185-201`） | 否（原型走派生） |
| 对 R1 的影响 | 数据库改动少 1 列，且不需要"防不一致"的补偿逻辑 | 多 1 列 + 回填 + 对账脚本 |

**结论（待确认）**：A 与需求 7.3「可售=实际−已锁未释放」（`需求文档.md:531`）**语义等价**，只是「已锁」不落列；B 是"把 7.3 的两个词各落一列"的字面实现。本文量化以 **A** 为基准，B 的增量见 §2.4。

#### M-3 售后粒度：加列 vs 子表

| 维度 | **① 现表加列（本文基准）** | **② 新建按行子表** |
|---|---|---|
| 表结构 | `aftersale` +`order_goods_id` +`number`（2 列） | 新增 `litemall_aftersale_item(aftersale_id, order_goods_id, number, amount)`；`aftersale` 作单据头 |
| 与需求契合度 | `BR-AS-01`（`:293`）「一次申请只针对 1 个订单行」⇒ 售后单:订单行 = **1:1**，加列即够 | 1:1 关系被拆成 1:N 结构，当前用不到 N |
| 历史数据 | 存量行 `order_goods_id` 为 NULL（`01` §7 显示存量可清空 ⇒ 实际影响为 0） | 存量行不建子行，查询需 LEFT JOIN 兼容 |
| 扩展性 | 若将来要"一单多行"需再改结构 | 天然支持一单多行 |
| 风险 | 申请表与售后单同表，字段会偏多（但都是在用的字段） | 多一次 JOIN；"单据头无行"的空态需要额外约束 |
| 量化影响 | 新增表 0、`aftersale` 10 列 | 新增表 +1、`aftersale` 8 列 + 子表 4 列 |

**结论（待确认）**：按「不做无用抽象」（与 §8 不做清单同一判据）本文倾向 ①；② 保留作为"未来一单多行"的备选。**若用户未来允许"一次申请多行"，则必须走 ②**——因为 ① 的 1:1 假设会被打破。

#### M-4 商户维度：加列 vs 只写文档

- 依据：决策 2（`需求基线.md:30`、`需求文档.md:594`）「仅在**商品、订单、售后单**层预留商户维度」；`BR-ADM-06`（`:441`）「业务语义保留『归属商户』维度，将来扩多商户不推翻数据；**售后单继承订单的商户归属不单独维护**」。
- ① 加列（本文基准）：`goods.merchant_id`、`order.merchant_id`（各 1 列，`DEFAULT 1`），售后单**不加列**（依 BR-ADM-06 明示继承）。
- ② 不加列：仅在设计文档记录"本店"语义，将来扩商户需要改表 + 回填。
- **结论（待确认）**：按字面要求本文按 ① 计数（+2 列）；若用户认为演示期不必落列，改回 ② 则列数 32→30（§2.4）。

#### 施工顺序的硬约束（三处，避免"加了约束又回填"的返工）

1. **先回填、后加唯一键**：`goods_product.sku_code` / `spec_value_ids` / `comment.order_goods_id` / `coupon_user(coupon_id,user_id)` 都必须**先去重/回填，再加唯一键**，否则 ALTER 直接失败。
2. **`sku_code` 允许 NULL**：唯一键下 `NULL` 可重复，避免存量行在回填前互相冲突（若用 `''` 作默认值，多行 `''` 会撞唯一键）。
3. **废弃列不 `DROP`**：`order` 的 6 个废弃列与 `coupon.limit` 本期只"停止写入 + 文档标注"，`DROP COLUMN` 属不可逆操作，留到 R3 后单独评审（`01` I-13 提示仓库外可能仍有手工脚本引用）。

| 资金动作落点 | pay 的 `POST /inner/pay/refund` | 同 A | order 直接写 `litemall_refund`（表跨服务） |
| `refund` 行写入方 | pay（`aftersale_id` 由 order 入参传入） | pay | order（需 order 引入 `RefundMapper` 或直连 pay 库） |
| 事务边界 | 两段式本地事务 + 幂等键 + 状态机补偿；**不新增 `@GlobalTransactional`**（全仓现恰好 3 处：`OrderServiceImpl.java:148/355/476`） | 新增第 4 处 `@GlobalTransactional`，Seata 依赖扩到 pay（pay 库需 `undo_log`） | 两段式（同 A） |
| 失败可见性 | 停在「退款中」+ `restock_status=2` 标红，符合 `BR-AS-16` `:310`、`BR-AS-12` `:305` | 全局回滚后"钱没退、库存没回"，用户看到的是"退款失败"，需另一套提示 | 同 A |
| 改动量 | pay +1 端点 +1 Feign 客户端（`PayClient`）+ order 1 段编排 | A + Seata 配置 + pay 库 `undo_log` + 回滚验证 | order 加 `RefundMapper` + 表归属/文档改写 + pay 侧若有读 `refund` 的端点须跨服务 |
| 风险 | 两段式非原子：资金已退、回补失败 → 靠标红 + 重试兜底（v1 的 `restock_status` 已为此设计） | 跨库全局回滚失败会留下更难查的脏数据，且与"失败停退款中并标红"的需求语义相反 | **破现有分层**；pay 的账单/退款查询要跨服务读，或形成双向依赖 |
| 回退难度 | 中（拆 `PayClient` + 端点 + 编排） | 高（回滚 Seata 依赖与 `undo_log`） | 高（表归属迁移） |

**结论（已确认 2026-11-01，选 A）**：A 与现有 3 处 `@GlobalTransactional` 的口径一致（跨服务"能本地补偿就不上全局事务"），失败态对用户可见、可重试；B 只在"资金与库存必须强一致"时才值得；C 破分层不推荐。**端点账：A/B 各 +1 对内（`POST /inner/pay/refund`），C 为 +0。**

### 6.3 存量单规格商品 → 默认 SKU 迁移（只写不执行）

目标：让存量商品在 R1 上线后可被"按规格下单"（`BR-GOODS-06` `:144`），且 `BR-GOODS-01`（上架至少 1 规格 `:139`）成立。**全程不改 `goods_product.id`**（见 §6.2 硬约束）。

| 步 | 动作 | 判定 | 失败处置 |
|---|---|---|---|
| **M1** | 全库备份（`mysqldump --single-transaction`，含 `litemall_goods`/`goods_product`/`goods_specification`） | 备份文件可 `--dry-run` 恢复 | 中止 |
| **M2** | 校验存量：`SELECT COUNT(*) FROM litemall_goods WHERE deleted=0`，与 `goods_product` 行数对照 | 记录"无 SKU 商品数" | 中止 |

**M3 的 SQL 草案（MySQL 8.0 语法；5.7 需降级为脚本，见 I-07）**

```sql
-- 【需人工确认】① 无 SKU 商品的默认维度（"规格"= 单一值"默认"）
INSERT INTO litemall_goods_specification (goods_id, specification, value, pic_url, add_time, update_time, deleted)
SELECT g.id, '规格', '默认', g.pic_url, NOW(), NOW(), 0
FROM litemall_goods g
WHERE g.deleted = 0
  AND NOT EXISTS (SELECT 1 FROM litemall_goods_product p WHERE p.goods_id = g.id AND p.deleted = 0);

-- 【需人工确认】② 默认 SKU：sku_code 由 goods_sn 派生（保幂等、可回滚识别）
INSERT INTO litemall_goods_product
       (goods_id, sku_code, specifications, spec_value_ids, price, number, url, add_time, update_time, deleted)
SELECT g.id,
       CONCAT(COALESCE(NULLIF(g.goods_sn,''), CONCAT('G', g.id)), '-D'),
       JSON_ARRAY('默认'),
       CAST(s.id AS CHAR),
       GREATEST(g.retail_price, 0.01),          -- BR-GOODS-09：价格必须 > 0
       0,                                        -- 库存先置 0，由 §9-Q15 决定是否给默认值
       g.pic_url, NOW(), NOW(), 0
FROM litemall_goods g
JOIN litemall_goods_specification s
  ON s.goods_id = g.id AND s.specification = '规格' AND s.value = '默认' AND s.deleted = 0
WHERE g.deleted = 0
  AND NOT EXISTS (SELECT 1 FROM litemall_goods_product p WHERE p.goods_id = g.id AND p.deleted = 0);
```

> **库存初始值必须是 0 还是某个演示值？** 需求只说"老商品落默认规格"，没说库存从哪来（`需求文档.md:621`）。置 0 会导致全部存量商品显示"暂时缺货"（`BR-GOODS-05` `:143`），演示效果差；给固定值（如 10）等于凭空造库存。**列入 §9-Q15 待用户确认，本文不替用户决定。**

**M4 的 SQL 草案**（已有 SKU 回填 `sku_code`；`spec_value_ids` 需 JSON 元素匹配，5.7 无 `JSON_TABLE`，建议用一次性脚本）

```sql
-- 【需人工确认】sku_code 回填（确定性、可复算）
UPDATE litemall_goods_product
SET sku_code = CONCAT(goods_id, '-', COALESCE(NULLIF(REPLACE(spec_value_ids, ',', '_'), ''), 'D'))
WHERE sku_code IS NULL;

-- 【需人工确认】校验：同一商品内 (spec_value_ids) 不得重复（BR-GOODS-02）
SELECT goods_id, spec_value_ids, COUNT(*) c
FROM litemall_goods_product
WHERE deleted = 0
GROUP BY goods_id, spec_value_ids
HAVING c > 1;
```

**M5 前置校验（不通过不许加唯一键）**

```sql
SELECT COUNT(*) FROM litemall_goods_product WHERE price <= 0 OR number < 0;   -- 期望 0（BR-GOODS-09）
SELECT COUNT(*) FROM litemall_goods_product WHERE sku_code IS NULL;           -- 期望 0
SELECT goods_id, COUNT(*) c FROM litemall_goods_product WHERE deleted=0
GROUP BY goods_id HAVING c = 0;                                               -- 期望 0 行
```

**回滚脚本（M1~M5 任一步失败）**

```sql
-- 【需人工确认】幂等识别：默认 SKU 一定以 '-D' 结尾且 number=0（M3 里同时写入的）
DELETE FROM litemall_goods_product WHERE sku_code LIKE '%-D' AND number = 0;

```

### 10.1 goods 只读 `litemall_order_goods`（服务边界例外，R1 保留）

| 项 | 内容 |
|---|---|
| 文件 | `backend/litemall-next/litemall-goods/src/main/java/com/litemall/mapper/OrderGoodsRefMapper.java`（43 行，`@Mapper` 接口，全仓无 XML） |
| SQL（逐字） | `@Select("SELECT COUNT(1) FROM litemall_order_goods WHERE goods_id = #{goodsId}")` → `long countByGoodsId(@Param("goodsId") Long goodsId)`<br>`@Select("SELECT COUNT(1) FROM litemall_order_goods WHERE product_id = #{productId}")` → `long countByProductId(@Param("productId") Long productId)` |
| 读写性 | **只读**：两条 `SELECT COUNT(1)`，无 INSERT/UPDATE/DELETE，不 Join 其它表，不写 `litemall_order_goods` |
| 服务对象 | `CI-12 POST /admin/goods/delete` → 409 `GOODS_IN_USE`（被订单行引用不可删）；`CI-11 PUT /admin/goods/update` → 409 `SKU_IN_USE`（SKU 被订单行引用不可删）。**同步判定**：删除/覆盖 SKU 前必须当场拿到引用数，否则会出现「删完再校验」的窗口 |
| 不加 `deleted=0` 的理由 | 逻辑删除的订单行**仍是历史引用**：删掉商品后历史订单再也展示不出商品名/规格（`OrderGoodsRefMapper.java:18-21` 类注释原文：「逻辑删除的订单行同样是历史引用，删除商品后历史订单就无法再展示商品名」）。故判据是「存在任一订单行（含已逻辑删除）」，不是「存在未删订单行」 |
| R1 保留的理由 | ①仓库内**没有**可承载该查询的对内端点（`OrderClient` 无任何 order_goods 查询方法；`CN-IN-01` 是**按 `order_goods_id` 单查**，回答不了「该商品被引用几次」）；②新增对内端点会动端点账（32 → 33）并牵动 03/05/07/08 四份文档的数字，R1 末期做不划算；③该查询**只读、单表、无写、无 Join**，破坏面被限制在「读了一张不属于自己的表」；④漏判代价不对称——误删商品会污染全部历史订单 |
| 技术债风险 | ①**表结构耦合**：`order_goods.goods_id`/`product_id` 改名或迁移会打断 goods 编译（编译期暴露，风险可控）；②**分库/换库不可用**：order 库独立部署或分片时该查询立即失效（**最可能的触发点**）；③破坏「服务只读自有表」门禁，后续评审若定为硬规则，此文件是唯一豁免点 |
