| 字段 | 类型 | 说明 |

   - 事务②失败：售后单**停在 3** + `restock_status=2`（标红「库存待回补」），由 **CN-08** 重试；**pay 不回调 order**（DR-17），双方以 `aftersale_id` 对齐；
   - **不新增** `@GlobalTransactional`（全仓现有 3 处：`OrderServiceImpl.java:148/355/476`）。
8. **BR**：`BR-AS-05`、`BR-AS-12`、`BR-AS-14`、`BR-AS-15`、`BR-AS-16`、`BR-AS-17`、`BR-AS-18`、`BR-AS-19`、`BR-AS-20`（全退退券）、`BR-AS-23`。

### 6.7 CN-IN-04 `GET /inner/order/locked-stock` — 未付款锁量聚合（供 goods 算可售；**t16 授权新增**）

1. **编号**：`CN-IN-04`｜**新增**（2026-11-01 captain 授权；来源：08 域盘点 `D-07b` —— `CN-13` 库存列表落在 goods 服务，但 goods 侧没有 `order`/`order_goods` 的 Mapper，拿不到「未付款占用」；Q2=A 已定**不加 `locked_number` 列**，故 `locked` 只能由 order 服务派生提供）。**无对外配对端点**（goods 直接 Feign 调用，同 `CN-IN-01` 的形态）。

4. **入参**（查询参数）

| 字段 | 类型 | 必填 | 约束 | 说明 |


| 字段 | 类型 | 说明 |

| `list` | array | 按 `productId` **升序**；无任何占用时返回 `[]`（不是 `null`，06 §4） |

**判定口径（最容易算错的地方，本文钉死）**
   - **计入**：`litemall_order.order_status = 101`（未付款）的订单下、`order_goods.deleted = 0` 的行的 `number` 之和，按 `product_id` 分组。

   - **关于 `end_time`（2026-11-01 事实更正，captain）**：委托口径原写「`order_status=101` 且 `end_time IS NULL`」。`litemall_order.end_time`（「订单关闭时间」）**在改造前就已存在**（`.dbwork/schema-before.sql:464`、`Order.java:120`），本次 `CD-05` 新增的是 `expire_time`/`close_type`/`user_deleted`/`merchant_id`，**不含** `end_time`——此前本文 v3 与 `08:803`、`04:756` 写的「无 `end_time` 列」是错的，以本节为准。但**判定仍只用 `order_status = 101`**：关单的唯一权威是 `order_status=103` + `close_type`（1 用户取消 / 2 超时 / 3 运营立即关单），而 `end_time` 现状只在关闭动作里写入（`OrderServiceImpl.java:375`），**历史行可能为空**，拿它做条件会漏算或错算；两者语义等价时取不依赖时间戳的那个。

### 6.8 CN-IN-08 `POST /inner/order/admin/order/{orderId}/try-complete` — 订单尝试完成（301→501 唯一写点）

1. **编号**：`CN-IN-08`｜**新增**（`03` v10 §5.3.1；口径卡 §4.4 / R-09）。**无对外配对**（服务间型），唯一调用方 = goods 的 `CI-36`。**301→501 的唯一写点**（R1 口径卡 §1.5 定了"唯一写点"但此前无端点承载，故 R2 补此端点）。
2. `POST /inner/order/admin/order/{orderId}/try-complete` ｜ **inner**
3. **用途**：某行评价落库后，判断「该订单已无'未退款且未评价'的行」⇒ 把订单从 **301（已收货）** 跃迁到 **501（已完成）**。没有它，C 端"已完成"是死栏、后台"待评价"永不收敛。
4. **入参**（**v8 修订：body 必填，来源 R2 实现**）
   - 路径 `orderId`（string，`order.id`）；无 query。
   - **body**（`OrderTryCompleteDTO`，JSON；两个字段均必填，ID 一律**字符串化**）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `orderGoodsId` | string | ✅ | `litemall_order_goods.id`：本次评价对应的**订单行** |
| `commentId` | string | ✅ | 评价主键，写入该行 `litemall_order_goods.comment` 作为「已评价」标记 |

   - **为什么必须有 body（不是设计冗余，别改回"无 body"）**：本端点做两件事、顺序不可交换——
     ① `UPDATE litemall_order_goods SET comment = #{commentId} WHERE id = #{orderGoodsId} AND order_id = #{orderId} AND deleted = 0 AND comment = 0`——**幂等闸门**（只有 `comment = 0` 的行才会被标记；重复调用/并发重放第二次 `affected = 0`，**不会覆盖**已有评价 id）；
     ② 按第 6 条三条件把订单 301 → 501。
     第 ① 步是"已完成"判定的**前提**：第 6 条 ② 号条件本身就在问"还有没有 `comment = 0` 的行"。若只给 `orderId`，服务端既不知道评价落在哪一行，也没法把 `comment` 置上 ⇒ ② 号条件永远不满足 ⇒ **"已完成"永不收敛**。原「无 body」写法会让任何照契约实现的调用方稳定 400，故 v8 以实现为准纠正。
   - 缺参 / 空白 / 非数字串 ⇒ **`400 PARAM_INVALID`**（`/inner/**` 裸语义，无 `Result` 包装）；`orderGoodsId` 不属于该 `orderId`、或该行 `comment ≠ 0` ⇒ 第 ① 步 `affected = 0`，**不得当作错误**（幂等闸门的设计意图），一律落到第 7 条的 `200 + changed=false`。
5. **出参**（**裸 DTO，不进 `Result`**，`/inner/**` 约定）

```json
{ "orderId": "1001", "orderStatus": 501, "changed": true }
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `orderId` | string | 回显 |
| `orderStatus` | int | 调用后的**当前**主状态（101/102/201/301/501/103）——`changed=false` 时调用方可据此判断原因 |
| `changed` | bool | 本次是否真的发生 301→501 跃迁 |

6. **判定（三条件全满足才跃迁，一条条件更新内完成）**
   ① 当前 `order_status = 301`；
   ② `NOT EXISTS`（该单 `deleted=0` 且 `refund_status=0` 且 `comment=0` 的行）—— 无"未退款且未评价"行（`comment=-1` 的超期不可评行**不参与**）；
   ③ **不得因"所有行已退款"而跃迁**：须再判 `NOT fullyRefunded`（`fullyRefunded = NOT EXISTS(... refund_status <> 2)`）。

```sql
-- 示意（实现以 mapper 为准；②③ 均为"存在性"判定，不加锁读）
UPDATE litemall_order o
   SET o.order_status = 501
 WHERE o.id = #{orderId} AND o.deleted = 0 AND o.order_status = 301
   AND NOT EXISTS (SELECT 1 FROM litemall_order_goods g
                    WHERE g.order_id = o.id AND g.deleted = 0
                      AND g.refund_status = 0 AND g.comment = 0)
   AND EXISTS     (SELECT 1 FROM litemall_order_goods g2
                    WHERE g2.order_id = o.id AND g2.deleted = 0
                      AND g2.refund_status <> 2);
```

7. **幂等/并发**：CAS；`affected = 0` **不是错误**——回读当前状态后一律返回 **200 + `changed=false`**（已是 501 ⇒ 并发已处理；仍是 301 ⇒ 条件不满足）。**禁止**把 `affected=0` 映射成 409：本端点由评价触发的后台跃迁驱动，不是用户动作（`06` §5.3 的"affected=0 → 409"针对**用户发起的写**）。
8. **禁止项（三禁止 + 一约束）**：禁写 `end_time`/`close_type`（这是"已完成"，不是"关闭"）；禁把 501 当作退款完成；**禁定时/批量刷 501**；**禁在 goods 的本地事务内调用**（必须在 `CI-36` 提交**之后**调用，否则订单先到 501、评价事务回滚会造成"已完成但无评价"）。
9. **错误码（HTTP 语义，`/inner/**` 不套 `Result`）**：`401`（`X-Internal-Token` 缺失/错误）；`404`（订单不存在或已逻辑删除）；`500`（数据库异常）。**不返回 403/409**。
10. **失败补偿**：调用方 best-effort —— 吞异常 + `WARN` + 日志异常计数（`CI-08.logErrorCount`），**不向用户报错**；残留风险 = 评价成功但订单停在 301，下一次任一行评价成功会重放（CAS 幂等）。登记为 **D-40**（`03` §10.3）。
11. **BR**：`BR-CM-01`、`BR-CM-04`（隐藏评价**不**回退 501）、需求 §6.2 第 4/5 步；口径卡 §1.5 / §2.3.4 / §4.4。

### 12.4 覆盖自检

- 本文出现的每个 `errorCode` 都能在本节或 `06` §1.2.1 找到登记：实测 22 个码面全部有归属（4 + 18）。
- **v7 补充**：`CN-IN-08`（§6.8）**不产生新码位** —— 它是 `/inner/**` 裸 DTO 端点，失败以 **HTTP 状态**（401/404/500）表达，无 `data.errorCode`；`affected=0` 一律 200 + `changed=false`（**不是** 409，见 §6.8 第 7 条）。
- 反向：本节列出的 18 个域内码**均在正文实际使用**，无「登记了却没人用」的空码。
- 命名规范：全大写蛇形；**语义确实独立才立码**（如 `AFTERSALE_TYPE_ILLEGAL` 与 `ORDER_STATUS_ILLEGAL` 分属不同域与不同触发），参数类一律并 `PARAM_INVALID`。
