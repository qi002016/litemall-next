**CD 归属本身正确**（每个 CD 都落在拥有该表 Mapper 的服务）。问题出在**跨服务调用链**：

#### 3.2.2 ❌ DR-01（blocker）：回补库存的端点被 03 自己废弃，R1 第 10 步无路可走

- 现状：`litemall_order` 服务回补库存的唯一通路是 `goodsClient.releaseStockBatch(...)`（`litemall-order/src/main/java/com/litemall/service/impl/OrderServiceImpl.java:542`，Feign 定义在 `litemall-api/src/main/java/com/litemall/client/GoodsClient.java:80`）；下单实扣是 `:271` 的 `deductStockBatch`。
- 03 的处置：`CX-04`（`/inner/goods/product/release`）+ `CX-05`（`release/batch`）**退役**（`03:653-654`），理由是 M-2 选 A 时"派生锁量下释放=状态变化，不需要写库存"。
- 矛盾：**"释放锁量"与"退货回补"是两件事**。R1 第 10 步明确要求「黑色/L：实际与可售均由 9 回到 10（**退货回补 +1**）」（`需求文档.md:480`），BR-AS-16 也要求"退款与回补同一操作"（`:310`）。而在 M-2 选 A 时，`number` 已在支付成功时被实扣（`OrderServiceImpl.java:271` 的语义移到支付成功），退款必须把 `number` **加回去**；此时既没有 `release`（被废弃）、也没有 `restock` 端点。
- 选 B 同样不解决：`03:654` 说选 B 时 `release` 改为"解锁定"（`locked_number -= n`），仍不是 `number += n`。
- **建议修法（二选一，写进 03 §4.5 + §5.3）**：
  - (a) 保留 `release/batch` 不废弃，把语义收窄为"关单释放（M-2 B：解锁定；M-2 A：no-op 或校验）"，并**新增** `POST /inner/goods/product/restock`（批量 `number += n`，按 `order_goods_id` 幂等，`restock_status` 落库）；`CX-04/CX-05` 相应撤回或改写为"仅新增 restock"。
  - (b) 复用 `deduct` 的负数语义——**不推荐**（`number` 可能被扣成负、条件更新 `number>=n` 失效，超卖防线被绕过）。

#### 3.2.3 ❌ DR-02（blocker）：退款执行的主体与调用方向未定义，`refund` 行归属 pay 服务

- 事实：`Refund` 实体 + `RefundMapper` 都在 `litemall-pay`（`litemall-pay/src/main/java/com/litemall/mapper/RefundMapper.java:16`；`PayServiceImpl extends ServiceImpl<RefundMapper, Refund>`，`PayServiceImpl.java:41`）；order 服务**没有** RefundMapper。
- 03 的处置：CN-07 把"执行退款（资金+回补同事务）"放在 order 的 `/inner/aftersale/refund`（`03:613`）；CD-08 又要给 `litemall_refund` 加 `aftersale_id`（pay 的表）。
- 缺口：`litemall-api` 只有 4 个 Feign 客户端（`GoodsClient`、`MarketingClient`、`OrderClient`、`UserClient`），**没有 `PayClient`**；现有方向是 pay→order（`OrderClient.java:44,53` 的 `markPaid`/`markRefunded`）。于是 order 无法反向调 pay 写退款行；若强加 `PayClient` 又形成 order↔pay 双向依赖。
- **建议修法**：在 03 §5.2 补一段"退款执行时序"：① 谁发起（admin→order 的 CN-07）；② 资金动作在哪（pay 的 `/inner/pay/**`，是否需要新增 1 个对内端点，须计入"对内 25"的账）；③ `refund` 行由 pay 写、`aftersale_id` 由 order 通过入参传；④ 失败补偿（`restock_status=2` 待回补）谁重试。补完须同步 §2 的端点计数（当前 25 会变成 26）。

#### 3.2.4 ❌ DR-03（high）：评价校验要 goods→order，但没有 order 侧的"订单行查询"对内端点

- 需求：BR-CM-01（`需求文档.md:375`）要求"仅已收货、未评价、未退款的订单行可评"，CI-36 也写了该校验（`03:565`）。
- 事实：`comment` 表在 goods；订单行在 order；`OrderClient` 只有 7 个方法（pay/info、pay/success、pay/refund、admin/list、admin/stats、admin/ship、admin/refund，见 `litemall-api/.../OrderClient.java:35-93`），**没有按 `orderGoodsId` 查状态的方法**；03 的 25 个新增对内端点里也没有。
- **建议修法**：新增 `GET /inner/order/admin/order-goods/{id}`（返回 `status/refund_status/commented`），计入对内端点账（25→26）；或把"可评判断"下沉到 order 侧提供 `canComment` 布尔，goods 只做落库。

#### 3.2.5 ❌ DR-04（medium）：跨服务统计口径缺失（`lowStockCount`）

- CI-08 出参 +`lowStockCount`、CI-100「同 CI-08」（`03:549,597`），但库存数据在 goods（`goods_product.number`），order 服务无 `GoodsMapper`（实测 order 只有 6 个 Mapper）。03 未写"order→goods 取低库存统计"的调用，也没说由 admin 侧聚合。
- **建议修法**：明确 `lowStockCount` 由 admin 侧调 CN-13 的 `/inner/goods/admin/stock/list` 聚合，或从 CI-08 出参中移除（改由前端另调 CN-13）。

#### 3.2.6 事务边界（Seata）是否说清 —— **部分说清**

- 现状事实：`common.yaml:70-88` 业务服务 `seata.enabled: true`（网关在 `application.yaml:68` 覆盖为 false，`02` 已述）；`@GlobalTransactional` 全仓 3 处（`OrderServiceImpl.java:148/355/476`）。
- 03 的新流程里，**支付成功实扣**（CI-97 → CI-42）与**退款+回补**（CN-07）都要跨 order↔goods↔pay，但 03 未声明这两条是否纳入 `@GlobalTransactional`、以及"远程调用成功但本地事务回滚"的补偿由谁做（`restock_status` 只覆盖回补失败，未覆盖扣减失败）。
- **建议**：在 03 §5.2 的 CI-97/CN-07 行各加一句事务声明（是否 `@GlobalTransactional`、幂等键、失败落哪个状态），否则实现期各写各的（DR-10）。

## 7. 最终结论

### 7.1 结论：**需修订后确认**

## 11. 事实更正（captain，2026-11-01，不改动 §0–§10 原文）

> 本节只记录**我复核后推翻**的一处事实，不重写评审结论。§10.4 与 §10.8 里凡以「`litemall_order` 无 `end_time` 列」为依据的句子，以本节为准。

### 11.1 被推翻的事实

- **§10.4 的判据有误**：§10.4 把「`07` §6.7 与 `08:803` 都写『`litemall_order` 无 `end_time` 列』」记为 ✅ 一致，并在 §10.8 结论里作为「跨文档一致」的正例。
- **实际**：`litemall_order.end_time`（`datetime`，注释「订单关闭时间」）**在本次改造之前就已存在** —— 证据：
  - `.dbwork/schema-before.sql:464`：`` `end_time` datetime DEFAULT NULL COMMENT '订单关闭时间' ``（改造前快照）
  - `docs/design/01-现状-数据库基线.md:720`（G-06）已记录「`end_time` 全仓只有 1 处写入（取消订单）」
  - 线上 `information_schema.COLUMNS` 复核：`end_time` / `expire_time`（新增）/ `close_type`（新增）/ `confirm_time` 四个字段并存
  - `db/migrations/2026-11-01-01-add-columns.sql` 对 `litemall_order` 只新增 `expire_time`/`close_type`/`user_deleted`/`merchant_id`，**不含** `end_time`
- **成因**：`07` v3 的 t16 与 `08` v2 的 t14 各自据 `03` 的 `CD-05` 列表反推，把「`CD-05` 没新增 `end_time`」误读成「库里没有 `end_time`」；两份文档因此**错得一致**，评审的跨文档一致性检查自然通过——这是「一致 ≠ 正确」的典型案例，建议后续评审把「两份文档一致」与「与库/源码一致」分开判。

### 11.2 已做的更正（不改判定口径，只改事实陈述）

- `07-接口契约-订单售后支付.md` §6.7 第 5 点：改为「`end_time` 改造前即存在，但现状只在关闭动作里写入、历史行可能为空；判定**只用 `order_status=101`**，关单权威是 `103` + `close_type`」。
