## 0. 三条不可动摇的前提

1. **信封不变**：所有对外响应仍是 `Result{code,msg,data}`（`litemall-common-core/src/main/java/com/litemall/domain/Result.java:11-14`），成功 `code=200`（`:20`）。不引入新的外层包装、不改字段名。
2. **三种鉴权面各自独立**，不得混用：`/app/**`（C 端，JWT `role=user`）、`/admin/**`（后台，JWT `role=admin`）、`/inner/**`（服务间，`X-Internal-Token`，网关不路由）。
3. **只增不删**：存量 84 个保留端点**签名一个不改**；需要新语义的一律新增端点或新增可选字段（见 §7 兼容策略）。

## 1. 响应信封与状态码

### 1.1 信封

```json
{ "code": 200, "msg": "OK", "data": { } }
```

- `code`：**业务码**，与 HTTP 状态码解耦；**业务层** HTTP 恒 `200`（`CommonExceptionAdvice` 统一兜底），前端只判 `code`。**唯一例外是鉴权层**——过滤器在进 Controller 之前就返回真实 `401`/`403`，见 **§1.1.1**（v3 新增）。
- `msg`：给人看的中文短句，**不承载逻辑**；前端不得对 `msg` 做字符串匹配做分支。
- `data`：失败时为 `null`。

### 1.1.1 鉴权层例外：真实 HTTP 状态码（v3 新增 · 实测口径）

> **一句话**：**进 Controller 之前**的拒绝用真实 HTTP 状态码；**进 Controller 之后**的失败才是「HTTP 200 + `data.errorCode`」。两个层面不得混用，也不得把本例外推广到业务层。

| 层面 | 谁在拒 | HTTP 状态码 | 响应体 | 前端处置 |
|---|---|---|---|---|
| **鉴权层**（网关 `AuthGlobalFilter` / 后台 `AdminAuthFilter` / 内部 `InnerApiInterceptor`） | Servlet `Filter`，**早于** Controller 与 `CommonExceptionAdvice` | **真实 `401` / `403`** | 仍是 `Result{code,msg,data}` 形状，但 `code` 与 HTTP **同值**；`data` 只可能为 `null` 或 `{"errorCode":"…"}` | 收到 `401` ⇒ 直接跳登录；`403` ⇒ 提示无权限。**不要**再按 `code===200` 判断全部响应 |
| **业务层**（Controller / Service / JSR-303 / `@RestControllerAdvice`） | Spring MVC 内部 | 恒 **`200`** | `code` = 业务码（400/404/409/500…）+ `data.errorCode` | 只判 `code` |

**为什么拿不到 200 包装**：`reject()` 直接 `response.setStatus(status.value())` 并手写 JSON（`litemall-admin/src/main/java/com/litemall/filter/AdminAuthFilter.java:126-132`）。此时还没有 Controller 调用栈，`CommonExceptionAdvice` 无从介入 ⇒ 只能给真实状态码；这不是"忘了包装"，是架构上包不住。

**后台鉴权层已实现的三类拒绝**（`AdminAuthFilter.java`，`2026-11-01` 实测）：

| HTTP | `msg` | `data` | 触发 | 代码位置 |
|---|---|---|---|---|
| `401` | 未登录或令牌无效 | `null` | 无 token / 签名错 / 过期 | `:90` |
| `401` | 登录状态已失效，请重新登录 | `{"errorCode":"SESSION_EXPIRED"}` | token 的 `ver` 与 Redis `auth:ver:<adminId>` 不一致（改密 / 重置密码 / 禁用账号后） | `:104`（约定见 `07` §1.6、`08` §6.8.2） |
| `403` | 无权访问管理端 | `null` | JWT `role` 非 `admin` | `:94` |

响应体实测样例（`SESSION_EXPIRED`）——注意 `code` 与 HTTP 都是 `401`，与业务层的"HTTP 200 + code=409"形状不同：

```json
{ "code": 401, "msg": "登录状态已失效，请重新登录", "data": { "errorCode": "SESSION_EXPIRED" } }
```

- **登记位置**：`SESSION_EXPIRED` 属**鉴权层**码，登记在 `07` §1.3；**不进** §1.2.1 通用码表，也**不计入**各域「errorCode 码位」计数（账目不变）。
- **不照抄到业务层**：业务失败一律 `HTTP 200 + code≠200`；`/inner/**` 的非 200 契约见 §2 与 `docs/impl/05-R2实施口径.md` §1.4。

### 1.2 错误码表（本期定稿）

| code | 语义 | 何时用 | 现状 |
|---|---|---|---|
| `200` | 成功 | 一切正常返回 | 已有（`Result.java:20`） |
| `400` | 参数/业务校验不合法 | 必填缺失、格式错、数量越界、状态不允许该操作 | 已有（`BadRequestException`） |
| `401` | 未认证/凭证失效 | 无 token、token 过期或签名错 | 已有（`UnauthorizedException`） |
| `403` | 无权限 | 角色不符、访问他人资源 | 已有（`ForbiddenException`） |
| `404` | 资源不存在 | 按 id 查不到、已被删除 | **新增** |
| `409` | 状态冲突/并发冲突 | 状态机不允许的跃迁、重复提交、乐观锁失败、幂等键复用但参数不同 | **新增** |
| `429` | 触发限流 | 券领取、评价提交等高频动作 | **新增（可选）** |
| `500` | 服务端异常 | 未预期异常、DB/中间件错误 | 已有（`BizIllegalException`/`DbException`） |

**设计取舍**：不引入 `4xxxx` 业务码段。理由——现有 5 个码已被两套前端按 HTTP 语义理解，扩成业务码段会让 `code===200` 之外的判断全部重写；本期只有 3 个新码，且都能用 HTTP 语义无歧义表达。**若后续需要更细的错误分类，走 `data.errorCode`（字符串，如 `ORDER_STATUS_ILLEGAL`）而不是改 `code`。**

### 1.2.1 域内 `data.errorCode` 总表（2026-11-01 定稿）

约束：`data.errorCode` **只用于前端差异化文案**，不得参与业务判断分支；**服务端不得只返回 errorCode 而省掉 `msg`**（`msg` 必须是人可读的中文句子）。命名全大写蛇形、动词/名词在前，全局唯一。

**登记分两层（2026-11-01 修订，回应评审 DR-29）**：

1. **通用码（本表负责）**：跨域复用、任何域都可返回的码，只在本表登记一次。当前 3 个：`PARAM_INVALID`（400，参数格式/取值非法，**通用兜底**，各域不再自造 `XXX_INVALID`）、`IDEMPOTENT_CONFLICT`（409，幂等键复用但参数不同，全局）、`RESOURCE_NOT_FOUND`（404，通用查不到；具体域可另设语义更强的码如 `ORDER_NOT_FOUND`）。
2. **域内码（07 / 08 各自负责）**：只在一个域内有意义的码（如 `ORDER_*`、`AFTERSALE_*`、`GOODS_*`），由该域的契约文档在文末**「errorCode 登记表」**登记，本表只收录已跨域确认的部分。判定标准：**同名字段在别的域也返回 ⇒ 进本表；反之进域内表**。

前端只按 `errorCode` 选文案、不参与分支，因此域内码不必跨文档齐备；但**每个契约文档必须把自己用到的每一个码都登记在案**（评审以此判定覆盖），且不得与本表或已注册的域内码同名异义。下表为当前已跨域确认的部分（订单/售后/库存/营销/支付/商品各域在 07、08 内另有完整登记表）。

| errorCode | 挂载 code | 触发 | 归属域 |
|---|---|---|---|
| `ORDER_NOT_FOUND` | 404 | 订单 id 查不到或非本人 | 订单 |
| `ORDER_STATUS_ILLEGAL` | 409 | 当前主状态不允许该动作（通用兜底） | 订单 |
| `ORDER_EXPIRED` | 409 | `expire_time <= now()`（§5.5） | 订单 |
| `ORDER_NOT_PAYABLE` | 409 | 非 101 进支付 | 订单 |
| `ORDER_ALREADY_PAID` | 409 | 并发重复支付 | 订单 |
| `ORDER_ITEM_LIMIT` | 400 | 订单行数超上限 | 订单 |
| `STOCK_NOT_ENOUGH` | 409 | 锁量失败，`msg` 带「规格 + 仅剩 N 件」 | 库存 |
| `ADDRESS_INVALID` | 400 | 地址已删 / 越权（越权也可用 403） | 订单 |
| `COUPON_NOT_USABLE` | 400 | 券不可用（门槛/状态/归属） | 营销 |
| `IDEMPOTENT_CONFLICT` | 409 | 幂等键复用但参数不同 | 全局 |
| `AFTERSALE_NOT_FOUND` | 404 | 售后单不存在 | 售后 |
| `AFTERSALE_STATUS_ILLEGAL` | 409 | 售后状态不允许该动作 | 售后 |
| `AFTERSALE_EXISTS` | 409 | 同一订单行已有未完结售后 | 售后 |
| `AFTERSALE_QTY_EXCEED` | 400 | 申请数量越界 | 售后 |
| `AFTERSALE_WINDOW_CLOSED` | 409 | 超 7 天申请窗口 | 售后 |
| `AFTERSALE_NOT_DELIVERED` | 409 | 待发货订单申请「退货退款」 | 售后 |
| `REFUND_AMOUNT_MISMATCH` | 400 | 前端传额与服务端算额不一致 | 售后 |
| `RESTOCK_PENDING` | 409 | 回补未完成却要置「退款完成」（内部原因，**不作为对外失败码**，见 §1.3） | 售后 |
| `PAY_MODE_INVALID` | 400 | 演示支付 `mode` 非 `success`/`fail` | 支付 |
| `GOODS_IN_USE` | 409 | 商品已被订单/售后引用，不允许删除（只能下架） | 商品 |

### 1.3 成功但「部分失败」

批量操作（批量退款、批量回补、批量发货）**不允许**用 `code=200` 掩盖部分失败：返回 `data` 中逐条结果 + 汇总，任何一条失败整体仍是 `200`，但 `data.failed>0` 时前端必须提示。

**「钱成功、库存没成功」不属于失败，属部分完成**：退款金额已原路退回但库存回补失败时，返回 `200` + `status` 仍停在「退款中」+ `restockPending: true`，由前端标红「库存待回补」，**不得**返回 `409 RESTOCK_PENDING`（否则前端会当成操作失败并重试退款，造成二次动钱）。`RESTOCK_PENDING` 只作为服务端拒绝置「退款完成」的内部原因，写入日志与 `data.reason`。

```json
{ "code": 200, "msg": "OK",
  "data": { "total": 3, "succeeded": 2, "failed": 1,
            "items": [ {"id": 11, "ok": true}, {"id": 12, "ok": false, "reason": "库存回补失败，已置待回补"} ] } }
```

## 2. 鉴权与身份传递

| 面 | 前缀 | 认证方式 | 身份来源 | 生效位置 |
|---|---|---|---|---|
| C 端 | `/app/**` | JWT（RS256，`litemall.jks`） | 网关注入 `userId` | `AuthGlobalFilter` + 服务侧 `UserContext` |
| 后台 | `/admin/**` | JWT（`role=admin`） | 网关注入 `adminId` | 同上 |
| 内部 | `/inner/**` | `X-Internal-Token` 静态令牌 | 无用户身份，调用方自带业务参数 | `InnerApiInterceptor` |

- **业务代码不得从请求体/参数里取 `userId`**，只能取当前上下文；后台同理取 `adminId`（售后审核人 `audit_admin`、操作日志 `admin_id` 都由此写入）。
- **`/inner/**` 的唯一例外**：内对端点没有用户上下文，凡需要写「操作人」的（售后审核、退款、改物流、关单），由调用方（admin 服务）**显式透传可选入参 `adminId`**；order 侧规则为「透传优先、缺失记 `null` 并在日志里留空」，**禁止**伪造 `0` 或猜测。
- `/inner/**` 端点一律**不做用户鉴权**，只校验令牌；因此**不得**把它们暴露到网关路由表。
- 免登录白名单（16 条）保持现状，新增白名单必须同时改网关 `hm.auth.roleRules` 与本文附录。
- **后台会话失效（退出登录 / 重置密码 / 禁用账号）用 Redis token 版本号实现，零加列**：键 `auth:ver:<adminId>`（无过期或与 token TTL 同寿），JWT 内携带 `ver` 声明，网关注入前比对 `auth:ver`；登出、改密、禁用账号时版本号 +1，旧 token 立即失效。**不新增「退出登录」端点**（前端丢弃 token 即可），重置密码与启停用走 §2 之后的账号端点。

## 3. 分页、排序、筛选

### 3.1 入参（复用 `PageQuery`，`litemall-common-mybatis/.../PageQuery.java`）

| 参数 | 类型 | 默认 | 约束 |
|---|---|---|---|
| `pageNum` | int | 1 | ≥1（**对外参数名沿用现状 `pageNum`**，8 个 admin Controller 均如此；`PageQuery.pageNo` 只是内部封装，契约层不得暴露 `pageNo`） |
| `pageSize` | int | 20 | ≥1，**上限 100**（超出按 100 处理，不报错） |
| `sortBy` | string | 端点自定义默认 | **白名单枚举**，非法值忽略并落默认（禁止透传为 SQL 列名） |
| `isAsc` | bool | true | 仅配合 `sortBy` 生效 |

> **例外登记（D3，2026-11-01）**：**后台订单列表（`CI-26`）默认 `isAsc=false`**（`addTime desc`，新单在前，见 `07` P-11）；售后单列表（`CN-01` 后台、`CN-15` C 端）按同一口径默认 `isAsc=false`（`applyTime desc`），见 `07` 对应入参表。其余列表一律沿用上表默认 `true`。显式传 `isAsc` 时均以入参为准。这三类列表是「默认 `true`」的**显式例外**，已在 `07` 与本文同步。

### 3.2 出参（复用 `PageVO`）

```json
{ "total": 128, "pages": 7, "list": [ ] }
```

`total`/`pages` 为 `Long`，**序列化为字符串**（`PageVO.java:19-24` 已声明 `type="string"`，保持），避免 JS 大数精度丢失。

### 3.3 筛选

- 同一维度多值用**逗号分隔**（如 `status=101,102`），不用数组重复参数。
- 区间筛选统一 `xxxMin` / `xxxMax`（金额为分、时间为毫秒时间戳或 `yyyy-MM-dd HH:mm:ss`，见 §4）。
- 关键词统一 `keyword`，**不得**出现 `kw`/`q`/`search` 三种写法（存量端点若已如此，保持；新增端点只用 `keyword`）。

## 4. 字段与类型约定

| 类别 | 约定 | 理由 |
|---|---|---|
| **金额** | 请求/响应一律**整数分**；库内 `DECIMAL(10,2)` 元，**只在服务边界转换**（Q1=A 已定） | 避免浮点误差；库不改类型，零 DDL 风险 |
| **ID** | `BIGINT`，**JSON 序列化为字符串** | JS `Number` 只能安全表示 2^53，订单号已 `bigint` |
| **时间** | `yyyy-MM-dd HH:mm:ss`（服务器本地时区，东八区）；仅需要日期时 `yyyy-MM-dd` | 与库内 `DATETIME` 一致；不用 epoch 毫秒，便利后台导出 |
| **布尔** | `true/false`，不用 `0/1` | |
| **枚举** | 数值码 + 独立 `xxxText` 文本字段，**前端不硬编码文案** | 文案要能改；状态码要稳定 |
| **枚举（存量字段）** | **现状已是字符串标识的字段不改成数值**，只**追加** `xxxText` 中文文案（如订单 `status` 保持 `unpaid`/`waitShip`…，新增 `statusText`） | 改类型＝两套前端全批改；追加字段＝零风险。**新增端点才用数值码 + Text** |
| **空值** | 对象字段可为 `null`；数组**永远返回 `[]` 不返回 `null`** | 前端遍历免判空 |
| **字符串** | 长度按库列上限，超长**拒绝**（400）而非静默截断 | |

**金额示例**：库中 `litemall_order.actual_price = 99.00`（元）→ 接口 `actualPrice: 9900`（分），字段名加 `Cent` 后缀吗？**不加**。约定"金额字段一律以分为单位"，靠命名文档与 Review 保证；新增字段名无需后缀，避免存量 84 端点字段名不一致。

## 5. 幂等、并发与状态机

1. **写操作幂等键**：下单 `/app/order/submit` 需带幂等键，**字段名沿用现状 `idemToken`**（`OrderSubmitDTO`，不改名以免破坏前端）；同键重放返回**首次结果**（`200` + 同 `orderId`），不重复下单；同键不同参数 → `409 IDEMPOTENT_CONFLICT`。
2. **库存回补幂等**：幂等**在 order 侧**——order 先对 `order_goods.restock_status` 做 CAS（`0→1`，`affected=1` 才调回补），goods 的 `/inner/goods/product/release` 入参**不变**（`productId`+`number`）、**不感知售后状态、不写 `restock_status`**（DR-18）；回补成功后 order 落 `restock_status=1`，失败落 `2`（待回补）并保留可重试。
3. **状态跃迁一律 CAS**：`UPDATE ... WHERE id=? AND status=?`，`affected=0` → `409`。禁止"先查后改"。
4. **状态机唯一权威**：订单状态机与售后状态机定义在 `需求文档.md` §5.5/§5.7 与 `03` §4；接口层只做校验与错误码映射。
5. **超时关单**：`expire_time` 由服务端写入（下单 +30min）；支付前必须校验 `expire_time > now()`，过期即 `409 ORDER_EXPIRED` 并触发关单。

## 6. 路径与命名

- 资源复数、小写下划线：`/admin/aftersale/list`、`/app/aftersale/{id}`。
- 动作型端点用动词后缀：`/admin/aftersale/approve`、`/inner/goods/product/deduct`。
- 新增端点**不得**复用已废弃端点的路径（废弃端点保留 1 个版本，返回 `410`？→ 本期直接下线，见 §7）。
- 每个端点必须有 `@Operation(summary=...)`，summary 写**用户可感知的动作**（如"审核通过售后单"），不写"查询列表"这类无信息量文案。

## 7. 兼容与废弃策略

| 变更类型 | 允许 | 做法 |
|---|---|---|
| 出参**新增字段** | ✅ | 直接加，前端忽略未知字段 |
| 出参**删除/改名/改类型** | ❌ | 新增端点，旧端点标 `@Deprecated` 保留 1 个迭代 |
| 入参**新增必填** | ❌ | 改为可选 + 服务端默认值 |
| 入参**新增可选** | ✅ | 直接加 |
| 错误码**新增** | ✅ | 见 §1.2 |

**两条例外（2026-11-01 裁定，避免误伤已定方案）**：
