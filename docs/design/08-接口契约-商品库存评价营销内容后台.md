## 2. 库存与 SKU

### 2.1 库存表达约定（本域所有库存端点共用）

**三级结构**：`商品(goods) → 规格维度/规格值(goods_specification) → SKU(goods_product)`。**精度到 SKU，无商品级库存**（需求 §7.3 `:531`）。

**三个量**（**Q2=A 派生锁量，库内没有 `locked_number` 列**，CD-02 `:309-329`、`03:244-261`）：

| 量 | 定义 | 来源 | 用途 |
|---|---|---|---|
| `number` | **实际库存** | `litemall_goods_product.number`（唯一持久化的量） | 库存调整的目标值 |
| `locked` | **已下单未付款占用** | **派生**：`Σ order_goods.number`，条件 = 订单 `status=101`（未付款）且 `expire_time > NOW()` 且 `order_goods.deleted=0`，按 SKU 聚合 | **只用于展示与前置提示** |
| `sellable` | **可售** | `sellable = number − locked`（下限 0） | C 端"库存状态"、加购上限、下单前置校验 |

**三个动作**（需求 §7.3 `:530-531`、D2）：

1. **下单锁定**：**不写任何库存列**（Q2=A）。锁量由"未付款订单行"的存在自然表达。
2. **支付成功转实扣**：`number = number − n`，**一次性、同单只转一次**，且**必须**是条件更新 `WHERE id=? AND number>=n`（affected=0 ⇒ 库存不足，这是**超卖唯一兜底**）。
3. **关单/取消释放锁**：**不写库存列**，锁量随订单转 `status=103` 自然消失（DR-09：已超时但未被关单的仍计入，直到订单转 103）。

> **`locked` 的数据来源（D-07b 已裁定，落点定死）**：`locked` 要读 `order_goods`/`order`，而 `goods` 服务**没有** order 相关 Mapper。**order 域新增对内 `CN-IN-04 GET /inner/order/locked-stock`** → `{list:[{productId, lockedQty}]}`（入参 `productIds` 可选、逗号分隔、≤200；只统计 `order_status=101` 且 `order_goods.deleted=0` 的订单行——**超时但尚未被关单（仍为 101）的仍计入**，已支付 102/已关单 103 不计入；判定**只用 `order_status`**——关单权威是 `103` + `close_type`，`end_time` 列虽存在（改造前即有，见 `.dbwork/schema-before.sql:464`）但现状只在关闭动作里写入、历史行可能为空，故**不作查询条件**）；该端点契约由 **07** 补，本文只**引用**、不定义。goods 的 `CN-13`（含对内 `/inner/goods/admin/stock/list`）调用它后计算 `sellable = number − locked`（下限 0）。
> **禁止加 `locked_number` 列**（Q2=A）：`locked` **永不落库、永不参与写路径**，只在读时派生。
> 若 order 不可达：`locked`/`sellable` 返回 `null` + `data.lockedUnavailable=true`（降级约定见 §2.2 错误码段），前端显示"—"，**不得把 null 当 0**（否则会把占用中库存当可售卖出去）。

**回补（Q24=A，D-10 已裁定）**：`POST .../release*` 的语义收窄为「按 `order_goods_id` 对应的订单行回补 `number += n`」；**幂等责任在 order 侧**——order 先对 `aftersale.restock_status` 做 CAS（`0→1`），成功后才调 goods 的 `release`（DR-18）。因此 goods **入参一字不改**（单条仍是 `productId`+`number`；批量仍是 `items[]`），**不接收 `orderGoodsId`、不感知售后单状态、不读写 `aftersale`**。
> **准确边界（必须写明）**：goods 的 `release` 端点**本身不是幂等的**（重复调用会重复加库存）；"只回补一次"由 order 的 CAS 保证。这是 Q24=A 的真实含义，也是**不采纳"加 `orderGoodsId` 入参"**（D-10 建议）的理由：入参加幂等键 = 改契约，而 03 已明确该端点「路径/入参/出参不变」。

**低库存**：`sellable ≤ 5`（常量 5，Q18 `需求文档.md:573`；**不加列、不加配置项**，D-15），后台标黄（BR-GOODS-10 `:148`）。

### 6.6 CI-04 · 重置密码（保留 · 实现方式变更、对外语义不变 · **D-08 已裁定**）

- **方法与鉴权**：`PUT /admin/account/reset-password` · admin（写日志）
- **用途**：重置某账号密码；**重置后旧会话立即失效**（BR-ADM-05）。
- **相对现状**：**保留**。路径/方法/入参（`AdminResetPwdDTO{id,password}`）/出参**一字不变**；仅**实现方式变更**（在 06 §7 的语义变更例外条款下允许）：改 `password` 后 **token 版本 +1**，旧 token 校验失败。
- **入参**：`id`（必填）、`password`（必填，6–32）。
- **出参**：`data=null`。
- **错误码**：400；404 `RESOURCE_NOT_FOUND`；500。
- **幂等/并发**：同一新密码重复提交结果一致（可视为幂等）；每次成功调用 token 版本 +1（幂等于"当前密码"层面）。
- **✅ D-08 已裁定（v2）——旧会话失效机制（零加列）**：Redis 键 `auth:ver:<adminId>` 存 token 版本号；登录签发的 JWT 内带 `ver` 声明；网关/admin 侧校验 `ver == auth:ver:<adminId>`，不等 ⇒ 401。**登出、改密、重置密码** 三个动作把该键 +1（登出由前端丢 token 触发，不新增端点）。零列、不动 03 表账。
  - ⚠️ 该机制要求 admin 侧能读 Redis：admin 服务当前无 Redis 依赖则需新增（属实现细节，不改契约，但**排期须计入**；登记 **D-08c**）。

### 6.8 CN-37 · 账号启用/禁用（**v2 转正 · D-08 已裁定**）

> **为什么转正**：需求 §5.14 ②「账号列表（新增、改密码、**禁用**，不可自删）」要求禁用能力，而 v1 基线**无端点、`litemall_admin` 也没有 `status` 列** ⇒ 需求有、能力无。v2：`litemall_admin.status TINYINT(1) NOT NULL DEFAULT 1` **已加列**（1 启用 / 0 禁用），端点转正。

- **编号 / 方法与鉴权**：**CN-37** · `POST /admin/account/status` · admin（**写日志**：账号停用属关键操作，参照 BR-ADM-03）
- **用途**：启用或禁用某个后台账号（目标态语义，非自增自减）。
- **相对现状**：**新增**（转正）。v1 的 `SUG-ADM-01` 撤销，编号统一为 CN-37。
- **重置密码不新增端点（v3 定稿）**：现状已有 `PUT /admin/account/reset-password`（`AdminController.java:71`，即 **`CI-04`**，路径/方法/入参/出参**均不变**）。本域**不新增** `POST /admin/account/reset-password`；重置密码只是**实现方式变更**——成功后把 Redis `auth:ver:<adminId>` **+1**，使该账号**旧 token 全部失效**（与登出、禁用共用同一条 `ver` 机制，零加列）。因此「账号管理」屏的重置按钮直接调 `CI-04`，前端无需区分两套接口。

**错误码**

| code | errorCode | 触发 |
|---|---|---|

#### 6.8.1 退出登录（**v2：不新增端点**）

- **裁定**：**不新增 `POST /admin/auth/logout`**。v1 的 `SUG-ADM-02` 撤销。
- **实现**：前端丢弃本地 token 即视为退出（BR-ADM-04 只要求"未登录跳登录页"，不要求服务端会话销毁）；若需"旧会话立即失效"，由前端在丢弃 token 前调用一次"token 版本 +1"的能力 —— **但该能力不开放为独立端点**，仅在 ①改密 ②重置密码 ③账号被禁用 三处由服务端各自 +1。

### 7.3 退款金额与 `unavailable[]` 的口径补充（无独立端点）

- **退款金额归期**：按**退款完成时间**（`aftersale` 进入 `refunded` 的时间）落在统计区间内统计，**不是**按订单支付时间；与 `refundRate` 分子**同源**（同一份 `refundCount`），避免"金额与单数口径不一致"。
- **待发货/待处理售后是"当前值"不是"期内值"**：`waitShipCount`/`pendingAftersaleCount` 取**请求时刻**的存量，不随 `period` 变化（原型 KPI 卡亦如此）；前端不要把它们的值当成"期内新增"。
- **失败降级**：任一指标取数失败 ⇒ 字段 `null` + 名称进 `unavailable[]`，整体仍 `code=200`（需求 §5.13「异常」）；**不得**因为 order/aftersale 不可达而让整个工作台 500。

## 11. errorCode 登记表（本域全量 · v4 新增 · DR-29）

> **编号说明**：本节即 `04` §10 终审 DR-29 所指的「08 文末 errorCode 登记表」。评审信按其条目序号称「§12」；本文 §0–§10 已连续占用，故编为 **§11**，两者指同一节。
> **登记依据**：`06` §1.2.1 为**两层登记**——① 通用码由 06 登记（`PARAM_INVALID` 400 / `IDEMPOTENT_CONFLICT` 409 / `RESOURCE_NOT_FOUND` 404）；② **域内码由本域契约文档在文末逐码登记**。本节完成 ②，并对可归通用码的一律归并（**本域不新增任何 `XXX_INVALID` 类码**）。
> **约束（同 06 §1.2.1）**：`data.errorCode` 只用于前端差异化文案，**不参与业务判断分支**；服务端**不得**只返回 errorCode 而省掉 `msg`（`msg` 必须是完整中文句子）；`code` 沿用 HTTP 语义，**不引入 `4xxxx` 业务码段**（§0.4）。
> **不适用面**：本文 §8 的 `/inner/**` 端点返回**裸类型**（无 `Result` 包装），错误走异常映射，**不返回 `data.errorCode`**，故不入本表。

### 11.1 覆盖口径（可复核）

**本域正文实际使用的 errorCode 字面量共 36 个**。测量口径（可复核）：对 `08-*.md` 全文提取大写蛇形 token（`[A-Z][A-Z0-9]+_[A-Z0-9_]+`）去重 → **38 个**，其中 2 个不计：`XXX_INVALID`（06 §1.2.1 的**禁令占位符**，非本域码，仅在本文引用禁令时出现）、`IDEMPOTENT_CONFLICT`（06 登记的通用码，**本域无幂等键端点、未使用**，仅在 §11.1 说明中提及）⇒ **实际使用 36 个**。按处置分为四类：

| 类别 | 个数 | 处理 |
| --- | --- | --- |
| ① 通用码（06 已登记，本域只引用） | 2 | `PARAM_INVALID`、`RESOURCE_NOT_FOUND` |
| ② 06 已跨域登记、本域沿用同一码位 | 1 | `GOODS_IN_USE`（06 表归属「商品」域） |

| ④ 独立域内码（本节唯一登记处） | 24 | 语义不可由通用码表达，逐条登记于 §11.4 |

> **与 06 的关系**：`IDEMPOTENT_CONFLICT`（409）在 06 登记，但**本域没有幂等键端点**，未使用，故不入表。`CONCURRENT_MODIFIED`（409）在本域 7 个改契约端点复用，语义跨域通用，**建议后续晋升到 06 §1.2.1**（属对 06 的建议，本轮不改 06，按域内码登记于 §11.4）。
