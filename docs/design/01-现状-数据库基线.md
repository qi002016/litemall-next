## 0. 一页结论（TL;DR）

1. **28 张表全部由实体类定义，仓库内没有基线 DDL。** 表名、列名、字段类型只能以实体类为准；唯一键、索引、外键、列精度、字符集**在仓库内不可得**（§5）。
2. 仓库内唯一的 SQL 文件是 `db-migration-M10-bigint.sql`（235 行），头部自述「本文件由整改过程生成，**未被任何任务执行过**」，内容只有 `MODIFY COLUMN int→bigint`，**不含 `CREATE TABLE`**，因此不是基线 DDL。
3. **28 张表的主键全部是 `id` + `IdType.AUTO`（数据库自增）**，无 UUID、无雪花、无业务主键（§2.2）。
4. **全部 28 个实体都有 `deleted` / `addTime` / `updateTime`，但全库 0 处 `@TableLogic`，配置里也没有 `logic-delete-field`。** 逻辑删除完全靠业务代码手写 `.eq(Xxx::getDeleted, false)` 过滤（§2.3）。
5. **金额在库里是 `BigDecimal`、单位是「元」**；唯一换算成「分」的地方是微信支付下单边界（`PayServiceImpl.java:121`）。**这与需求 7.2「最小单位为分」（`需求文档.md:528`）直接冲突**（G-13）。
6. **多规格 SKU 的骨架已存在，但缺 3 样东西**：`litemall_goods_product` 无 SKU 编码/无规格维度外键/无库存锁定列；规格组合只以 JSON 字符串存在 `specifications` 列，DB 层无法约束「同商品规格组合不重复」（G-01/§2.6）。
7. **订单行已经存了 SKU 标识（`product_id`）与规格文字快照（`specifications`）与单价快照（`price`）**，`BR-GOODS-07` 的三个要素字段齐备（G-02）。
8. **售后单只到「订单」粒度**：`litemall_aftersale` 有 `order_id`，**没有 `order_goods_id`**，全仓库 `orderGoodsId|order_goods_id` grep 零命中；代码把 `type` 硬编码为 1、`amount` 直接取前端传值（G-03）。
9. **没有库存锁定字段、没有超时关单任务**：下单即实扣（条件 UPDATE 直减），全仓库无 `@Scheduled`/`@EnableScheduling`/`DelayQueue`/`xxl-job`（G-05、G-06）。
10. **没有商户（tenant）字段**：`tenant|merchant|shop_id|store_id` grep 零命中（G-07）。
11. **`coupon_user` 的「一人一券」在 DB 层没有唯一约束**：唯一索引整段被注释在 SQL 里，领取路径无校验、靠 Redis 计数限流（G-04）。
12. **`db-migration-M10-bigint.sql` 覆盖 36 张表，比 28 个实体多 8 张**（groupon / issue / keyword / notice_admin / permission / region / role / system）：这些表在仓库内无实体。**2026-11-01 实测已确认：8 张全部真实存在**，行数 `region` 3231 / `permission` 31 / `system` 18 / `keyword` 7 / `issue` 4 / `role` 3 / `groupon` 0 / `notice_admin` 0（**6 张有数据、2 张空**）（G-12、I-02）。
13. **28 个 Mapper 全部是 `extends BaseMapper<T>` 的空接口**，无 `@Select`/`@Update`/自定义 SQL、无 mapper XML。所有查询条件都以 Java lambda 表达，因此索引使用情况只能从这些条件反推（§5.3）。
14. **需求侧「只保商品 / 账号 / 地址」（`需求文档.md:126`、`:601`）中，C 端用户与收货地址没有对应的「数据保留」条文**：`5.14 数据保留`（`:444`）只覆盖后台管理员账号。该歧义列入 §8（I-11）。

- **【直证】**：直接从文件读到的内容（带 `文件:行`）。

## 2. 全局横切事实（适用于全部 28 张表）

### 2.1 表 ↔ 实体 ↔ 服务的对应

- 实体分布：goods 8、marketing 6、order 6、pay 1、user 2、storage 1、message 2、admin 2 = **28**。
- 注意 admin 服务的两个实体放在 `domain/` 直下（不是 `domain/PO/`）：`litemall-admin/src/main/java/com/litemall/domain/AdminAccount.java:24`、`.../AdminOperationLog.java:24`，其余 26 个都在各自模块的 `com/litemall/domain/PO/` 下。
- Mapper 路径统一为 `<服务模块>/src/main/java/com/litemall/mapper/<实体名>Mapper.java`，共 28 个（`find . -name "*Mapper.java"` 计数 = 28），全部形如 `public interface GoodsMapper extends BaseMapper<Goods>`，**无一个含自定义 SQL 注解或 XML**（全仓 `find -name "*.xml"` 在 `src/main` 下无 mapper XML）。本文后续每表只给 Mapper 简单名。

### 2.2 主键与自增方式

- 28/28 均为 `@TableId(value = "id", type = IdType.AUTO)`【直证，逐文件行号见 §3.2 各表小节】。即**主键由数据库自增生成**，应用不参与发号。
- 全局配置同向确认：`litemall-common-core/src/main/resources/common.yaml:63-70` 段内 `mybatis-plus.global-config.db-config.id-type: auto`、`update-strategy: not_null`【直证】。
- **`litemall_storage` 的主键 Java 类型是 `Integer`，其余 27 张表是 `Long`**（`litemall-storage/src/main/java/com/litemall/domain/PO/Storage.java:33` vs 其余 `private Long id`）【直证】。这是全库唯一的类型不一致点；`db-migration-M10-bigint.sql` 的 int→bigint 迁移是否覆盖它见 §5.1。

### 2.3 逻辑删除：有字段，无框架支持

- 28/28 实体都声明 `private Boolean deleted`【直证，逐文件计数：28 命中】；`@TableLogic` 在全仓 **0 命中**；`logic-delete` / `logicDelete` 在 `*.java` / `*.yaml` / `*.yml` 中 **0 命中**【直证】。
- 后果【推断】：MyBatis-Plus 不会自动追加 `deleted = 0`，**任何漏写 `.eq(getDeleted, false)` 的查询都会读到已删行**。现状代码是逐处手写的，例：`GoodsServiceImpl.java:147`、`:166`；`GoodsServiceImpl.java:129`（products 过滤）；`OrderServiceImpl.java` 的订单列表查询同理。这是后续所有改动的**横切风险点**，不是某一张表的问题。
- 物理删除现状：商品删除是软删（`GoodsServiceImpl.java:211-225` 置 `deleted=true`），且**不级联** products / specifications。

### 2.4 时间戳

- 28/28 实体都含 `private LocalDateTime addTime` 与 `private LocalDateTime updateTime`【直证，28/28】。
- **没有自动填充**：全仓无 `MetaObjectHandler`【未发现】；`addTime`/`updateTime` 由业务代码显式 `setAddTime(LocalDateTime.now())` / `setUpdateTime(...)` 写入，例 `GoodsServiceImpl.java:174`、`:182-183`、`:205`、`:222`。
- 后果【推断】：任何绕过 Service 的写入（新写的 SQL、批量脚本）都不会自动带时间戳。
- 例外：`litemall_address` 用 `@TableField` 显式写列名 `add_time` / `update_time`（`Address.java:94`、`:100`），其余表依赖驼峰自动映射（`map-underscore-to-camel-case` 默认开启）。

### 2.5 金额单位：元（与需求 7.2 冲突）

- 全部金额字段的 Java 类型都是 `BigDecimal`【直证，见 §3.2】。业务注释里也未见「分」口径。
- **单位是「元」的直接证据**：`backend/litemall-next/litemall-pay/src/main/java/com/litemall/service/impl/PayServiceImpl.java:121` —— `info.getActualPrice().movePointRight(2).intValue() != result.totalFeeCents()`，即**只有在调用微信支付时才 ×100 转成分**。
- **反向佐证**：全仓 grep `/100`、`multiply(100)`、`movePointLeft` 无落库换算命中（唯一命中 `PayServiceImpl.java:64` 的是毫秒/1000 取时间戳，与金额无关）【直证】。
- **冲突事实**：需求 7.2 明确「最小单位为**分**」（`需求文档.md:528`），并定义「行小计 = 单价 × 数量」（`:528`）。现状库内是元、无行小计字段。→ 见 G-13、G-17。
- 其余金额字段：`order.goodsPrice/freightPrice/couponPrice/integralPrice/grouponPrice/orderPrice/actualPrice/refundAmount`、`goods.counterPrice/retailPrice`、`goods_product.price`、`brand.floorPrice`、`coupon.discount/min`、`topic.price`、`aftersale.amount`、`refund.amount`、`groupon_rules.discount`。

### 2.7 无商户（tenant）维度

- 全仓 grep `tenant|merchant|shop_id|store_id|storeId`：**唯一命中是支付侧「商户订单号」文案**（`WechatPayV3NotifyForVerifier` 相关行 `:138`、`:143`），**没有任何业务表字段**【直证】。
- 需求侧要求「业务语义上保留『归属商户』这一维度」（`需求文档.md:441` BR-ADM-06、决策 2 `:594`）。→ G-07。

### 2.8 无库存锁定（锁量）语义

- `litemall_goods_product` 只有 `number`（`GoodsProduct.java:44`）一个整型库存列，**无 locked / reserved / frozen 列，无版本号/乐观锁列**【直证】。
- 扣减是条件 UPDATE 直减：`GoodsInnerController.java:106-121`（`.ge(GoodsProduct::getNumber, number)` + `setSql("number = number - {0}", number)`，`rows==0` 抛「库存不足」）；回补 `setSql("number = number + {0}")` 在 `:127-133`；批量版 `:145-190`。
- 所以现状是「**下单即实扣**」（`OrderServiceImpl.java:271`），没有需求 7.3（`需求文档.md:530-531`）的「锁量增、实际不变」中间态。→ G-05。
- **易混淆项**：`CouponServiceImpl.java:62-64` 的 `STOCK_RESERVED_KEY` 是**优惠券**库存的 Redis 预减台账，不是商品库存锁【直证】。

### 2.9 数据库连接与库名

- 默认库名 `litemall`：`litemall-common-core/src/main/resources/common.yaml:37`
  `jdbc:mysql://${HM_DB_HOST:127.0.0.1}:${HM_DB_PORT:3306}/${HM_DB_NAME:litemall}?useUnicode=true&characterEncoding=UTF-8&autoReconnect=true&serverTimezone=Asia/Shanghai`【直证】。
- 时区 `Asia/Shanghai` 与需求 7.4「全站同一时区 Asia/Shanghai」（`需求文档.md:533-534`）一致【直证】。
- 未观察到 HikariCP 之外的连接池配置、未观察到多数据源；Seata 相关配置开启（`common.yaml`），因此 `undo_log` 表在线上可能存在——**仓库内无该表实体**【未发现】，见 I-08。
