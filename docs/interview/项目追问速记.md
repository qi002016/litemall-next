## 2. 一次下单到底发生了什么（先建立全局图）

```
浏览器 H5
  │ ① POST /app/order/submit   （带 Authorization + idemToken）
  ▼
网关 8000  AuthGlobalFilter
  │ · 剥掉外部自带的 user-info / X-Internal-Token（防伪造）
  │ · 校验 RS256 JWT 签名 → 解析出 userId/role/aud
  │ · 按路径前缀校验 role + aud
  │ · 注入 user-info: 42 转发给下游

  │ ② Redis Lua：幂等 token INIT → USED（原子）
  │ ③ 校验地址、可售库存、算券额、按行分摊券（尾差入末行）
  │ ④ INSERT litemall_order（status=101 未付款, expire_time=now+30m）
  │ ⑤ afterCommit 投递 RocketMQ 延时消息（30 分钟后关单）
  │ ⑥ INSERT order_goods × N（行快照：单价、券分摊、实付金额）
  │ ⑦ Feign → marketing 8003：核销优惠券（/inner/coupon/use）
  │ ⑧ 清购物车
  ▼ 事务提交（任一步抛异常 → Seata 回滚全局）
返回 orderId + orderSn + expireTime

30 分钟后 → RocketMQ 消息 → order 消费 → closeExpiredOrder()
  │ CAS 101 → 103 → 回退优惠券 + 留痕
```

**关键点（一定要讲出来）**：下单**不扣 `goods_product.number`**，锁量完全由 `order_status=101` 派生；支付成功那一跳才真正扣减。这个设计决定了后面所有库存逻辑的口径。

## 3. 库存并发控制

### 3.1 他会怎么问

- "你怎么防超卖？"
- "为什么不用 `synchronized` / Redis 分布式锁？"
- "库存拆三量是什么意思？锁定量为什么要派生？"

### 3.2 一句话答法

> 用 `UPDATE ... SET number = number - n WHERE id = ? AND number >= n` 加影响行数判定，把"判断够不够"和"减"压进同一条 SQL，数据库行锁保证原子性，替代"先查后写"的竞态窗口；批量扣减按 `productId` 升序固定加锁顺序避免交叉死锁。

### 3.3 展开：超卖是怎么发生的

"先查后写"在并发下的经典交错：

```
时间  线程A                      线程B                     DB.number
 t1   读到 number=1                                         1
 t2                              读到 number=1              1
 t3   判断 1>=1 够 → 更新 1-1=0                              0
 t4                              判断 1>=1 够 → 更新 1-1=0   0   ← 卖了 2 件，超卖
```

把判断写进 `WHERE` 之后，两线程的 UPDATE 会在数据库行锁上串行：

```java
// litemall-goods/src/main/java/com/litemall/service/impl/StockServiceImpl.java:298
@Override
public void deduct(Long productId, Integer number) {
    validateChange(productId, number, "扣库存参数错误");
    boolean ok = goodsProductService.lambdaUpdate()
            .eq(GoodsProduct::getId, productId)
            .eq(GoodsProduct::getDeleted, false)
            .ge(GoodsProduct::getNumber, number)      // ← 判断进 WHERE
            .setSql("number = number - {0}", number)  // ← 减法在 DB 里做，不在内存里算
            .update();                                 // ← 返回 affected rows
    if (!ok) {
        throw GoodsApiException.paramInvalid("库存不足");   // 影响行数 0 = 不够
    }
}
```

**三个细节，答出来就是加分项**：

1. **`number = number - n` 而不是先在 Java 里算好再 `set`**：后者在并发下会丢更新（两线程都读到 10，都写 9）。
2. **用影响行数判定，不用"再查一次"**：`affected = 0` 就代表条件不满足，而"再查一次"又多了一个竞态窗口。
3. **`ge(number, n)` 是"至少够 n 件"**，`deleted=false` 一起进条件，避免扣已删除 SKU。

### 3.4 为什么不用悲观锁 / 分布式锁

| 方案 | 为什么不选 |
|---|---|
| `synchronized` / `ReentrantLock` | 只锁单 JVM，多实例部署直接失效 |
| Redis 分布式锁（Redisson） | 能防超卖，但每扣一次库存多一次 Redis RTT + 锁续期风险；库存是**单行热点**，数据库行锁本来就够，加一层不如不加 |
| `SELECT ... FOR UPDATE` 悲观锁 | 事务持有行锁直到提交，热点 SKU 下排队严重、容易拖长事务 |
| 乐观锁 version 字段 | 冲突时失败要重试，高并发下重试风暴；条件更新等价于"带业务条件的乐观锁"，但不需要额外列 |

> 一句话：**能用一条 SQL 解决的事，不要用分布式锁**。锁只解决"互斥"，条件更新还顺带表达了业务约束。

### 3.5 库存三量：实际 / 锁定 / 可售

- `number`（DB 里的实际库存）
- `locked`（锁定量，**不落库**，按订单状态实时聚合）
- `sellable = number - locked`（可售）

锁定量为什么派生？看这条 SQL：

```java
// litemall-order/src/main/java/com/litemall/mapper/OrderMapper.java
/**
 * R1（CN-IN-04）：按 SKU 聚合「锁定量」——order_status=101 AND og.deleted=0 的 number 之和。
 * · 只认 101：102/201/301/501/103 都不计入（已支付即转实扣）
 * · 超时未关单仍计入：不带任何时间条件
 * · 库内一次 GROUP BY 聚合，禁 N+1
 */
@Select("""
        SELECT og.product_id AS productId, SUM(og.number) AS lockedQty
        FROM litemall_order o
        JOIN litemall_order_goods og ON og.order_id = o.id AND og.deleted = 0
        WHERE o.deleted = 0 AND o.order_status = 101
        ...
        GROUP BY og.product_id
        """)
```

**为什么不存一张 `locked` 冗余列**：

1. 冗余列要靠每个状态迁移点去 ±，**漏一处就对不上账**，最后得写定时任务核对——这是负债，不是设计。
2. 状态派生天然幂等：状态对了，聚合就对了；重复关单、重复支付都不会把数字改错。
3. 代价是一次聚合查询。控制方式是**接口层批量**：goods 展示库存页时，把所有 `productId` 一次性传给 order（`lockedStock(List<Long>)`，上限 200 个），order 一次 `GROUP BY` 返回，禁止 N+1。
4. 降级：这条 RPC 挂了，`sellable` 显示 `null` + `lockedUnavailable=true`，前端显示「-」而不是报错——**列表页不该因为算不出锁定量就整页挂掉**。

### 3.6 批量扣减为什么按 productId 升序

```java
// StockServiceImpl.java:327 deductBatch()
List<StockChangeDTO.Item> ordered = new ArrayList<>(items);
// 固定加锁顺序（productId 升序），避免并发下单互相等待造成死锁
ordered.sort(Comparator.comparing(StockChangeDTO.Item::getProductId,
        Comparator.nullsLast(Comparator.naturalOrder())));
for (StockChangeDTO.Item item : ordered) { ... 逐条条件更新 ... }
// 任一条失败 → 抛 InsufficientStockException，由 @Transactional 整批回滚
```

如果 A 单要扣 [SKU1, SKU2]，B 单要扣 [SKU2, SKU1]，不排序就可能互相持有对方要的行锁 → 死锁。统一升序后，两个事务的加锁顺序一致，只会短暂等待，不会循环等待。

**注意**：结果**按请求原顺序**返回（`inRequestOrder`），因为前端要按自己的行顺序渲染——加锁顺序和返回顺序解耦。

### 3.7 追问预判

| 追问 | 答法 |
|---|---|
| "影响行数为什么会是 0？" | 三种情况：库存不够（`ge` 不满足）、SKU 已删除、id 不存在。业务上统一按"库存不足"返回，日志里再区分 |
| "扣成功了但后面事务回滚了怎么办？" | 这就是 Seata 的作用，见第 4 节；本地 `@Transactional` 保证同服务内回滚，全局事务保证跨服务回滚 |
| "热点 SKU 每秒几百单扛得住吗？" | 诚实答：单行热点下数据库行锁本身就是瓶颈，压测没做过；要做的话是**分段库存**（把一行拆成 N 行分桶）或**预扣 + 异步落库**，我没做，因为项目量级不需要 |
| "锁定量算出来是旧的呢？" | 会有毫秒级延迟。所以它是**展示量**不是**扣减依据**：真正扣减只认 `number`，`sellable` 只用于前端置灰和下单前的友好提示 |

## 4. 分布式事务（Seata AT）

### 4.1 他会怎么问

- "跨服务怎么保证一致性？"
- "Seata AT 的原理？"
- "既然库存用了条件更新，为什么还要 Seata？"（**这题答好直接拉开差距**）

### 4.2 一句话答法

> 下单要同时做三件事：order 建单、goods 扣库存、marketing 核销券，分在三个服务三个库，本地事务管不了，所以用 Seata AT 的 `@GlobalTransactional` 包住入口；AT 靠 undo_log 记录数据快照做反向补偿，对业务代码零侵入。

### 4.3 代码

```java
// litemall-order/src/main/java/com/litemall/service/impl/OrderServiceImpl.java:271
@Override
@GlobalTransactional(rollbackFor = Exception.class)   // ← 全局事务边界
public OrderSubmitVO submitOrder(OrderSubmitDTO dto) {
    // ... 幂等 token → doSubmitOrder(dto, userId) ...
}

private OrderSubmitVO doSubmitOrder(OrderSubmitDTO dto, Long userId) {
    // ① 校验（地址、可售、券）
    // ② INSERT litemall_order（101 未付款）
    saveOrder(order);
    orderTimeoutPublisher.publishAfterCommit(order.getId(), order.getExpireTime());
    // ③ INSERT order_goods × N
    // ④ Feign → marketing：useCoupon(use)
    marketingClient.useCoupon(use);
    // ⑤ 清购物车
}
```

### 4.4 AT 两阶段到底做了什么（通俗版）

把 AT 想成"**自动记账 + 自动补录**"：

- **一阶段**：每个分支服务执行本地 SQL 时，Seata 代理数据源偷偷多干两件事——把**改之前的行镜像（before image）**和**改之后的行镜像（after image）**写进本地 `undo_log` 表，然后本地事务提交。**所以一阶段就把数据改了**（这是 AT 和 TCC 最大的区别）。
- **二阶段提交**：全局都成功，异步删掉各库的 `undo_log`，收工。
- **二阶段回滚**：谁失败了，协调器通知各分支用 `undo_log` 里的 before image 生成**反向 SQL** 恢复数据；恢复前还要校验"这行有没有被别人改过"（`after image` 对不上就说明脏写，报错让人工介入）。

三个必须知道的代价：

1. **全局锁**：一阶段提交后，被改的行会被 Seata 的全局锁保护到二阶段结束，其他全局事务要改这些行得等——**长事务会放大冲突**，所以下单链路里我尽量不做慢操作（不发 MQ 同步消息、不调外部支付）。
2. **undo_log 表**：每个业务库都要建，占空间。
3. **只保证"最终回滚"，不保证隔离**：并发全局事务之间可能读到中间态（脏读），需要业务自己用条件更新兜住。

### 4.5 关键题：既然有条件更新，为什么还要 Seata？

这是最能体现你真想过的题。标准答法：

> **两者解决的不是同一个问题**。
> - 条件更新解决**单行数据的并发正确性**：同一 SKU 被两个人同时抢，保证不超卖。它防的是"同一条数据被并发改坏"。
> - Seata 解决**跨服务操作的原子性**：order 建单成功了、marketing 券也核销了、但 goods 扣库存失败，前面两步必须撤销。它防的是"做了一半"。

举个具体场景说明：订单里 2 行商品，第一行扣成功、第二行库存不足。这时：
- 条件更新只保证了"第一行没扣坏、第二行没扣成"，**它不会帮你把第一行退回去**；
- 靠 `@GlobalTransactional`，异常抛出后 Seata 用 undo_log 把第一行库存、已核销的券一起撤掉，用户看到的是"下单失败，什么都没发生"。

反过来说：只有 Seata 没有条件更新，两个并发请求都通过"可售校验"，一阶段各自执行 `number = 可售数 - 1` 的**绝对值写入**，照样超卖——所以两者必须同时有。

### 4.6 为什么不选 TCC / Saga / 本地消息表

| 方案 | 判断 |
|---|---|
| **TCC** | 要为每个参与方写 Try/Confirm/Cancel 三套接口，业务侵入大；本项目"扣库存"没有真正的资源预留语义（锁量是派生的），写 TCC 反而绕 |
| **Saga** | 适合长流程、每步都要补偿的业务；这里链路只有 2 跳、要的是"全成或全不成"，Saga 的中间态暴露代价不值得 |
| **本地消息表 / 事务消息** | 解决的是"本地事务 + 异步通知"的最终一致（比如下单后发短信）；这里要求的是**同步失败即整体失败**，语义不同 |
| **不用分布式事务，靠对账** | 电商常规做法是大促场景，但本项目量级小、要的是"用户点下单要么成要么败"，AT 够且最省事 |

**诚实的补充**（面试官很吃这套）：AT 是"能跑通、够用"的选择，不是"最优"选择。如果 QPS 上去、链路变长，我会换成"本地消息表 + 补偿任务"或按业务拆分 Saga，因为 AT 的全局锁在高并发下会变成瓶颈。

### 4.7 追问预判

| 追问 | 答法 |
|---|---|
| "全局事务里调 Feign 有什么坑？" | 超时会拖长全局事务、放大全局锁持有时间；所以内部调用都设了超时，且下单链路只调两个必须同步的接口（核销券），其他（发消息、写统计）全部异步或事后 |
| "undo_log 里存什么？" | 表名、主键、before/after image（JSON）、回滚 SQL；二阶段回滚时先校验 after image 与当前数据一致再执行反向 SQL |
| "AT 模式下 Feign 调用失败会怎样？" | Feign 抛异常 → 方法异常 → `@GlobalTransactional` 标记回滚 → 协调器通知已提交的分支用 undo_log 回滚 |
| "全局事务 ID 怎么传的？" | Seata 通过 `RootContext`（ThreadLocal）绑定 XID，Feign 拦截器把它塞进请求头透传；Python agent 那种非 Java 进程不参与全局事务 |

## 5. 接口幂等（防重复下单）

### 5.1 他会怎么问

- "用户连点两下提交订单会生成两个订单吗？"
- "你怎么做的幂等？"
- "为什么用 Lua？"

### 5.2 一句话答法

> 服务端先发一个一次性 token，提交时必须带上；用一段 Redis Lua 脚本把"读状态 + 改状态"做成原子操作，token 在 INIT → USED 之间只允许成功推进一次；同 token 同参数直接回放首次结果，同 token 不同参数返回 409。

### 5.3 状态机

```
createIdemToken()  →  SET order:idem:{token} = INIT  EX 300s
                          │
                   用户点"提交订单"
                          ▼
              ┌──── Lua 原子推进 ────┐
              │  MISSING   → 400（token 不存在/过期）
              │  INIT      → USED，放行  （第一次）
              │  ROLLED_BACK → USED，放行（上次业务失败，允许重试）
              │  USED      → 进回放分支
              └──────────────────────┘
                          │
        业务成功 → 缓存"首次结果"（参数指纹 + VO）
        业务失败 → Lua 把 USED 改回 ROLLED_BACK（允许重试，但同 token 不同参数依然 409）
```

### 5.4 代码

```java
// OrderServiceImpl.java:165
private static final DefaultRedisScript<String> IDEM_MARK_SCRIPT = new DefaultRedisScript<>(
        "local v = redis.call('GET', KEYS[1]) "
      + "if not v then return 'MISSING' end "
      + "if v == 'INIT' or v == 'ROLLED_BACK' then "
      + "  local ttl = redis.call('TTL', KEYS[1]) "
      + "  if ttl and ttl > 0 then redis.call('SET', KEYS[1], 'USED', 'EX', ttl) "
      + "  else redis.call('SET', KEYS[1], 'USED') end "
      + "  return 'OK' "
      + "end "
      + "return 'USED'", String.class);
```

```java
// OrderServiceImpl.java:282
String state = stringRedisTemplate.execute(IDEM_MARK_SCRIPT, List.of(idemKey));
if (state == null || IDEM_MISSING.equals(state)) {
    throw new BadRequestException("幂等token无效或已过期", PARAM_INVALID);
}
if (IDEM_USED.equals(state)) {
    // 同键同参 → 回放首次结果；同键不同参 → 409 IDEMPOTENT_CONFLICT
    OrderSubmitVO replay = replayIdemResult(reqKey, fingerprint);
    if (replay != null) return replay;
    throw new ConflictException("幂等token已用于不同参数的提交，请刷新后重试", CODE_IDEMPOTENT_CONFLICT);
}
```

### 5.5 为什么必须用 Lua

三个看似都能用、实际都有坑的替代方案：

| 方案 | 问题 |
|---|---|
| `GET` 判断完再 `SET` | 两步之间不是原子的：两个并发请求都读到 `INIT`，都判断"可以放行"，**都下单成功**——幂等形同虚设 |
| `SETNX` | 只能表达"第一次"，表达不了 `INIT/USED/ROLLED_BACK` 三态；而且失败回滚时需要"改回可重试"的语义，`SETNX` 做不到 |
| Redis 事务 `WATCH/MULTI/EXEC` | 能实现，但冲突时客户端要自己重试，代码复杂度高；Lua 在服务端一次执行完，天然原子且只需一次 RTT |

**一句话**：Redis 单线程执行 Lua 脚本，脚本内部的所有命令之间不会被其他请求插入，这就是"原子"的来源。

### 5.6 两个容易被追问的细节

**① 为什么要"参数指纹回放"而不是简单拒绝重复请求？**

用户网络超时重试时，他最想要的是**看到自己刚才那单**，而不是"操作太频繁"。所以：同 token 同参数 → 返回第一次的 `orderId/orderSn`（用户无感）；同 token 不同参数 → 说明前端把同一个 token 用在了两笔不同订单上，这是 bug，返 409 让人发现。

指纹怎么算：把关键入参（收货地址、券、购物车项/立即购买项）排序后序列化再哈希，存在 `order:idem:req:{token}` 里，格式是 `参数指纹|OrderSubmitVO JSON`。

**② 业务失败为什么要把 USED 改回 ROLLED_BACK？**

如果库存不足导致下单失败，token 已经变 USED，用户改小数量再提交就会撞"已使用"——体验直接坏掉。所以失败时回滚状态，允许**同 token 重试**；但因为指纹校验还在，**不同参数仍然拒绝**，不会变成"一个 token 下单两次"。

### 5.7 TTL 与遗留问题（要敢讲）

- TTL 是 **5 分钟**（`RedisKeys.ORDER_IDEM_TTL_SECONDS = 300`），既是 token 有效期也是状态机生命周期。
- 过期后：前端再提交拿到 `MISSING` → 提示刷新页面重新获取 token。**这是有意的保守设计**：宁可让用户重来一次，也不接受"状态未知的 token 继续用"。
- **已知缺口（诚实说）**：如果 Redis 挂了，幂等闸门失效——此时靠数据库唯一键 `uk_order_sn` 兜底，重复提交会撞唯一键异常，但**不会自动回放结果**，用户会看到报错。这是可用性与正确性的取舍，不是没想到。

## 6. 订单超时自动关单（RocketMQ 延时消息）

### 6.1 他会怎么问

- "未付款订单怎么自动关闭？"
- "为什么用 RocketMQ，不用定时任务扫表？"
- "消息重复消费/丢失怎么办？"

### 6.2 一句话答法

> 下单时把"截止时间"写进订单，同时在事务提交后投一条 RocketMQ 延时消息（按剩余秒数映射到最近的延时等级），到点消费端执行关单；关单本身靠订单状态 CAS 保证幂等，另外留一个定时兜底扫描处理消息丢失，形成"主通道 + 兜底"双保险。

### 6.3 为什么不用定时扫表（这题一定要答）

- 扫表是**轮询**：5 分钟一次，最坏晚 5 分钟关单，锁量白占；
- 数据量上去后 `WHERE order_status=101 AND expire_time<=now` 要么全表扫、要么依赖索引+分页，**扫表频率与实时性直接矛盾**；
- 多实例部署还得抢锁（否则重复处理），要么加分布式调度（XXL-Job），要么自己写 CAS 抢单；
- 而延时消息是**事件驱动**：到点就有一次精确回调，扫表频率无关实时性。

> 但扫表**不是完全不要**：它是最可靠的兜底（不依赖 MQ 可用性），所以最终方案是两者并存——这是关键的架构判断，不要只说"用了 MQ"。

### 6.4 延时等级映射（细节题）

RocketMQ 4.x 的延时是**固定 18 个等级**（1s、5s、10s、30s、1m、2m…2h），不是任意时间。所以要把"剩余多少秒"映射到"不小于它的最小等级"：

```java
// litemall-order/src/main/java/com/litemall/mq/OrderTimeoutPublisher.java:45
private static final int[] DELAY_LEVEL_SECONDS = {
        1, 5, 10, 30, 60, 120, 180, 240, 300, 360, 420, 480, 540, 600, 1200, 1800, 3600, 7200
};

static int delayLevelOf(long remainSeconds) {
    if (remainSeconds <= DELAY_LEVEL_SECONDS[0]) return 1;
    for (int i = 0; i < DELAY_LEVEL_SECONDS.length; i++) {
        if (remainSeconds <= DELAY_LEVEL_SECONDS[i]) return i + 1;
    }
    return DELAY_LEVEL_SECONDS.length;   // 超过 2h 用最高级
}
```

30 分钟 → 1800s → `delayLevel = 16`。**注意是"向上取整"**：宁可晚到一点点（消费端会二次校验是否真到期），也不能早到就 ACK（见 6.6 的真坑）。

### 6.5 为什么必须 afterCommit 投递

```java
// OrderTimeoutPublisher.java:60
public void publishAfterCommit(Long orderId, LocalDateTime expireTime) {
    if (!enabled || orderId == null || expireTime == null) return;
    if (TransactionSynchronizationManager.isSynchronizationActive()) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() { send(orderId, expireTime); }
        });
    } else {
        send(orderId, expireTime);      // 无事务上下文（如单测直调）
    }
}
```

三个理由，都要能说：

1. **避免孤儿消息**：事务回滚了但消息已发 → 消费端收到一个不存在的订单（虽然会被 `order==null` 挡住，但这是靠下游兜的，属于设计缺陷）。
2. **避免"消息早于数据可见"**：事务未提交时其他连接读不到这个订单，消费端可能读到 `null` 就 ACK 掉。
3. **发送失败不能拖垮下单**：`send` 里 `catch` 只记 ERROR，不抛——MQ 抖动绝不能让用户下单失败，兜底扫描会补上。

### 6.6 消费端幂等 + 我踩到的真坑（讲故事）

```java
// OrderServiceImpl.java:908
@Override
@GlobalTransactional(rollbackFor = Exception.class)
public boolean closeExpiredOrder(Long orderId) {
    Order order = orderMapper().selectOne(/* id + status=101 + deleted=false */);
    if (order == null) return false;                      // 已支付/已关闭/不存在 → 直接 ACK
    if (LocalDateTime.now().isBefore(order.getExpireTime())) {
        orderTimeoutPublisher.publishAfterCommit(orderId, order.getExpireTime()); // 补投，见下
        return false;
    }
    try {
        closeUnpaidOrder(order, CLOSE_TIMEOUT, null, LOG_CLOSE_EXPIRED, "超时未支付…", "订单状态已变更，无需关单");
        return true;
    } catch (ConflictException e) {
        return false;                                     // 与支付/兜底并发，已有人处理
    }
}
```

**幂等的三道闸**（回答"重复消费怎么办"）：
1. `selectOne(status=101)`：非未付款状态直接跳过；
2. `closeUnpaidOrder` 里 CAS `101 → 103`（`WHERE order_status=101`）：影响行数 0 就抛 `ConflictException`，谁成功谁生效；
3. 兜底扫描与 MQ 同时命中同一单，也只会有一方 CAS 成功。

**我踩的真坑（这条非常值钱，一定要讲）**：

> 真机联调时把保留时长临时改成 1 分钟，第一单正常关了，第二单**永远没关**。
> 查日志发现消息到达时间是 `14:08:25.766`，而订单的 `expire_time` 是 `14:08:26`——**早了 234 毫秒**。
> 原因叠了三层：① 延时等级是秒级取整；② MySQL `DATETIME` 默认**不存毫秒**，写进去就被截断；③ broker 投递有抖动。
> 结果是消费端一上来就判"还没到期"，直接 ACK——这条消息就永久浪费了，订单再也没人管。
> 修法是：**提前到达时不 ACK 而是补投一条更短的延时消息**（剩余不足 1 秒就投 1 秒级），每轮 remain 递减，最多再跳一次就收敛。
> 修完实测：第一次 `closed=false` → 1 秒后 `closed=true`，订单状态变成 `canceled / 已关闭`。

**这个坑教会我**：分布式定时依赖"时间"，而时间在系统里至少有三个来源（应用时钟、DB 精度、MQ 调度），任何一处不精确都会让"到点执行"变成"永远不执行"。所以凡是基于时间的补偿，**必须能自愈**，不能假设只触发一次。

### 6.7 兜底扫描与死信

```java
// OrderTimeoutFallbackScheduler.java:31
@Scheduled(initialDelayString = "${hm.order.timeout-scan.initial-ms:60000}",
           fixedDelayString  = "${hm.order.timeout-scan.ms:300000}")
public void scanExpiredOrders() {
    CloseExpiredResultDTO result = orderService.adminCloseExpired(200, false);
}
```

覆盖三种 MQ 管不了的情况：① 投递失败；② broker 长时间不可用；③ 消息进了死信队列没人处理。
多实例都会扫，但关单是逐单 CAS，重复扫描只会得到 `affected=0`。

**消费端异常策略**：只有"业务上无需处理"才 `return false`（正常 ACK）；DB 不可用这类真异常**向上抛**，交给 RocketMQ 重试，超过上限进死信，兜底扫描是最后一道闸门。

### 6.8 追问预判

| 追问 | 答法 |
|---|---|
| "消息堆积怎么办？" | 关单消息体积极小（两个 Long），且消费是逐单 CAS、无外部依赖；真堆积时加消费线程/实例即可。生产上应该配监控告警，我没做 |
| "订单支付成功了，延时消息还会到吗？" | 会。所以消费端第一步就按 `status=101` 过滤，已支付直接 ACK |
| "为什么不用 Redis 过期键监听？" | Redis 过期是**惰性删除 + 定期删除**，不保证准点回调；且 key 过期事件不可靠（重启/主从切换会丢），不能做资金/库存相关的事 |
| "更精确的定时怎么做？" | 时间轮 + 分片扫描（Dubbo 的 HashedWheelTimer / XXL-Job 分片），或者 RocketMQ 5.x 的任意时间定时消息（`timerWheel`） |
| "ack 丢了会怎样？" | 消息重投 → 消费端 CAS 幂等，第二次 `closed=false`，无副作用 |

## 7. 支付回调（另一条幂等线）

```java
// OrderServiceImpl.java:981 markPaid()
if (order.getPayTime() != null) {                    // ① 幂等闸门：已处理过
    result.setApplied(false); result.setDeducted(false); return result;
}
if (Objects.equals(order.getOrderStatus(), CANCELED)) {   // ② 已关单还收到支付
    log.error("[DR-11] 已关闭订单收到支付成功回调，需人工退款…");
    return result;
}
// ③ 库存校验（不足则保持 101，不置待发货、不自动退款 —— P-31 冻结口径）
if (!shortage.isEmpty()) { ... return result; }
// ④ CAS 101 → 201（待发货）
boolean ok = lambdaUpdate().eq(Order::getId, order.getId())
        .eq(Order::getOrderStatus, UNPAID) ... .set(Order::getOrderStatus, UNDELIVERED) ... .update();
if (!ok) { result.setApplied(false); return result; }
// ⑤ 实扣库存（跨服务）
DeductBatchResultDTO deduct = goodsClient.deductStockBatch(...);
```

**四个设计点**：
1. **`pay_time` 是幂等标记**：支付服务可能重复回调（第三方支付本来就会重试），`pay_time != null` 直接返回，库存只扣一次。
2. **状态 CAS 而不是 if 判断后 update**：防并发（用户点取消和支付回调同时发生）。
3. **库存不足不自动退款**（P-31 口径）：订单保持 101，返回 `deducted=false` + 缺口，由人工/后续补偿处理。**这是产品决策不是技术缺陷**，讲的时候要说明"为什么这么定"——自动退款涉及真实资金动作，演示环境没有真实支付通道，贸然自动退会造成对账黑洞。
4. **已关闭订单收到支付成功**：只打 ERROR 日志 + 人工介入，因为"钱收了货没了"只能靠退，不能靠改状态掩盖。

## 8. 按行售后状态机

### 8.1 他会怎么问

- "售后状态有哪些？怎么防止非法跳转？"
- "退款金额怎么算？优惠券怎么分摊？"
- "退完货库存怎么回补，会不会重复加？"

### 8.2 8 个状态

```java
// litemall-order/src/main/java/com/litemall/constant/AftersaleStatus.java
APPLIED=0        已申请
WAIT_RETURN=1    待买家退货
WAIT_RECEIVE=2   待商家收货
REFUNDING=3      退款中
COMPLETED=4      已完成（终态）
CLOSED=5         已关闭（终态）
REJECTED=6       已拒绝（终态）
CANCELLED=7      用户取消（终态）
UNFINISHED = {0,1,2,3}     // "未完结"集合，用于查重
CLOSABLE   = {0,1,2}       // 可关闭集合
```

**按行（`order_goods`）而不是按单**：一单三件商品，可以只退其中两件、另一件正常收货。所以售后单挂在订单行上，**同一订单行同时只允许 1 个未完结售后单**。

> ⚠️ **注意措辞**：这个约束是**索引 + 应用层查重 + CAS**，不是数据库唯一键。
> 原因："未完结"是一个状态集合（0/1/2/3），MySQL 普通唯一键表达不了"仅在这些状态值下唯一"（除非用生成列）；所以用 `idx_as_order_goods(order_goods_id, status)` 支撑查重查询，`countUnfinishedByLine(og.getId()) > 0` 就拒绝。
> 简历上写"唯一键 + CAS 双约束"是**不准确的**，要改成"索引 + 状态 CAS + 应用层查重"。

### 8.3 状态跃迁一律 CAS

```java

```

退款那段最能说明为什么：


两个管理员同时点"同意退款"，只有一个能把 `2→3` 改成功，另一个拿到 409 ——**资金调用只会发生一次**。如果写成"先查状态是不是 2，再 update"，两人都能通过检查，就会重复退款。

### 8.4 退款金额怎么算

```java
// AftersaleServiceImpl.java  refundAmount()
BigDecimal actual = og.getActualAmount();          // 该行实付（已扣掉券分摊）
BigDecimal ratio = BigDecimal.valueOf(number)
        .divide(BigDecimal.valueOf(total), 6, RoundingMode.HALF_UP);   // 件数占比，保留 6 位
return Money.fen(actual.multiply(ratio).setScale(2, RoundingMode.HALF_UP));  // 再四舍五入到分
```

**券分摊在更早一步就做完了**（下单时）：

```java
// litemall-order/src/main/java/com/litemall/support/OrderRules.java  allocateCoupon()
for (int i = 0; i < size - 1; i++) {
    BigDecimal share = coupon.multiply(lineAmounts.get(i)).divide(goodsAmount, 2, HALF_UP);
    if (share.compareTo(lineAmounts.get(i)) > 0) share = lineAmounts.get(i);  // 防御：不超过该行金额
    allocated = allocated.add(share);
}
// 尾差入最后一行：保证 Σ各行分摊 == 券总额，不产生 1 分钱黑洞
BigDecimal last = coupon.subtract(allocated).setScale(2, HALF_UP);
```

**为什么要分摊**：一张 10 元券用在 30 元 + 70 元的订单上，如果只退 30 元那件商品，该退多少钱？必须按行占比把券摊下去（3 元 vs 7 元），否则退款金额和实付对不上，财务对不了账。尾差入末行是为了**保证分摊之和精确等于券额**，否则会出现"退完所有行还多退 1 分"。

### 8.5 库存回补的幂等

```java
/* 回补库存：先 CAS restock_status 0/2→1，成功才调 goods release。
   goods 侧不幂等，幂等由本方法 CAS 保证；release 抛异常时把状态挂回 2（待重试）。 */
```

`restock_status`：`0 未回补 / 1 已回补 / 2 待回补（失败）`。
- 只有 CAS 成功的那一次才真的调 `releaseBatch`；
- 调用失败把状态**挂回 2**，交给 `retryRestock` 重试；
- **资金已退就不能把售后单回滚成失败**，只能把"回补"标成待处理——这是"钱的事优先正确"的原则。

**回补矩阵**（`needRestock`，`AftersaleServiceImpl.java:751`）——这张表面试官很爱问"为什么已发货的仅退款不回补"：

| 订单状态 | 仅退款（type=1） | 退货退款（type=2） |
|---|---|---|
| 201 待发货（未发货） | ✅ 回补 | ✅ 回补 |
| 301/501/已收货（已发货） | ❌ **不回补** | ✅ 回补 |

逻辑：货还在自己仓库里才谈得上"加回去"。已发货但只退款 → 货在买家手里，加库存就是虚增；只有买家把货退回来才回补。

```java
// AftersaleServiceImpl.java:751
private boolean needRestock(Order order, Aftersale a) {
    Integer status = order.getOrderStatus();
    boolean refundOnly = Objects.equals(a.getType(), AftersaleStatus.TYPE_REFUND_ONLY);
    if (Objects.equals(status, OrderStatus.UNDELIVERED)) return refundOnly;
    if (SHIPPED || CONFIRMED || COMPLETED) return !refundOnly;
    return false;   // 其他状态不回补
}
```

**已知缺口（要主动说）**：这套矩阵是**按状态粗判**的，没有考虑"退货退款但买家没寄回"的边界——退货单有 `return_deadline` 和自动关单，超时关单时库存不会被误加，但如果买家寄回了货、商家却拒收，走的是人工流程。真实电商这里往往要"收货确认才回补"，本项目按"确认收货即回补"简化了。

### 8.6 追问预判

| 追问 | 答法 |
|---|---|
| "退款要不要退运费？" | 本项目运费恒为 0（单商户包邮），所以没实现运费退款规则；真要做要按"整单退才退运费"处理 |
| "券什么时候退回？" | 只在整个订单**全部行都退完**时才退券（`rollbackCouponIfFullyRefunded`），且失败不阻断已完成结果 |
| "退款先调资金还是先改状态？" | 先 CAS 本地置"退款中"→ 再调资金 → 成功后才置"完成"。中间任何一步失败，单子停在"退款中"可重试，**不会出现"资金退了但单子显示未处理"** |
| "重复回补会多加库存吗？" | 不会，`restock_status` CAS 挡在 `release` 之前；`release` 本身不幂等，所以幂等必须由调用方保证 |

## 9. 网关统一鉴权

### 9.1 他会怎么问

- "鉴权放在哪一层？"
- "JWT 用什么算法，为什么？"
- "内部接口怎么防绕过？"

### 9.2 一句话答法

> 鉴权统一放在网关：RS256 验签 JWT，按路径前缀校验角色和受众（aud），然后把用户 ID 作为 `user-info` 头注入下游；下游只信这个头。内部接口 `/inner/**` 走另一套共享密钥，网关会**先剥掉外部自带的所有身份头和密钥头**，再决定是否注入，防止外部伪造。

### 9.3 代码（剥头这一步是重点）

```java
// litemall-gateway/src/main/java/com/litemall/filter/AuthGlobalFilter.java:36
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    ServerHttpRequest request = exchange.getRequest();
    String path = request.getPath().toString();
    // ② 剥离外部自带的身份/内部密钥头（H1/H3：防止绕过网关鉴权伪造 user-info 或 X-Internal-Token）
    ServerHttpRequest.Builder cleaner = request.mutate().headers(headers -> {
        headers.remove(USER_INFO_HEADER);                 // "user-info"
        headers.remove(InnerApiProperties.HEADER);        // 内部密钥头
    });
    if (isExclude(path)) return chain.filter(exchange.mutate().request(cleaner.build()).build());
    TokenPrincipal principal;
    try {
        principal = jwtTool.parseToken(token);            // RS256 验签 + 过期
        checkRole(path, principal);                       // roleRules：/admin/** → admin + aud
    } catch (UnauthorizedException e) { return complete(resp, UNAUTHORIZED); }
      catch (ForbiddenException e)   { return complete(resp, FORBIDDEN); }
    // ⑥ 由网关权威注入
    ServerWebExchange swe = exchange.mutate()
            .request(cleaner.header(USER_INFO_HEADER, String.valueOf(principal.userId())).build())
            .build();
    return chain.filter(swe);
}
```

**为什么必须"先剥再注"**：如果不剥，外部请求自己带一个 `user-info: 1`（管理员 ID）就能冒充任何人。剥掉之后，下游看到的 `user-info` 只可能来自网关。

### 9.4 为什么用 RS256 而不是 HS256

HS256 是**对称**的：签名和验签用同一个密钥，意味着**每个能验签的服务都持有签发密钥**，任何一个服务被攻破都等于能签发任意用户的 token。
RS256 是**非对称**的：私钥只放在 user 服务（签发），公钥分发给网关（验签），验证方拿到公钥也无法伪造 token。

代价是密钥管理（本项目用 JKS 里的私钥/公钥对，通过环境变量 `HM_JKS_LOCATION/ALIAS/PASSWORD` 注入，缺配置直接启动失败——fail-fast）。

### 9.5 受众（aud）校验解决什么

`role=admin` 这个声明本身不够：如果 C 端用户 token 里被塞了 `role=admin`（越权发放），或者两个系统的 token 格式相同，光看角色会串权。加 `aud (audience)` 区分"这个 token 是发给哪个前端的"：`/admin/**` 要求 `aud=litemall-admin`，`/app/**` 要求 `aud=litemall-app`。

### 9.6 内部接口 `/inner/**`

- 调用方：服务之间走 Feign；
- 认证：共享密钥头（`HM_INTERNAL_TOKEN`，dev 容忍空但打 WARN，非 dev 空则启动失败）；
- Feign 出站由拦截器自动附加，业务代码不感知；
- 下游 `InnerApiInterceptor` 校验密钥，不通过直接 403。

**诚实边界**：这套方案防的是"外部伪造请求"，**防不住"攻击者已经进了内网"**。真正的生产方案是网络隔离（内部服务不暴露端口）+ mTLS + 服务网格；共享密钥是同机演示环境下的合理折中，讲的时候要主动说清楚。

### 9.7 追问预判

| 追问 | 答法 |
|---|---|
| "为什么不用 Spring Security？" | 网关是 WebFlux 响应式栈，Spring Security 的 `WebSecurityConfigurer` 是阻塞模型的；只做"验签 + 角色匹配"用 GlobalFilter 更轻。业务服务里的方法级鉴权我用了自定义 `UserContext` |
| "Token 过期怎么处理？" | 网关返回 401，前端清本地 token 跳登录；刷新令牌方案没做（演示环境 10 分钟 TTL + 重新登录可接受） |
| "下游怎么信任 user-info？" | 靠"服务不对外暴露端口 + 网关剥头"两层；`UserInfoInterceptor` 只读不写，`UserContext` 是 ThreadLocal，请求结束清理（防线程复用串用户） |
| "限流/熔断做了吗？" | Sentinel 依赖在但**没启用**（`sentinel.enabled=false`），这是我知道的缺口；要做的话在网关按 IP/用户维度配 QPS 规则 |

## 10. 缓存一致性

### 10.1 他会怎么问

- "缓存怎么设计的？"
- "怎么保证缓存和数据库一致？"
- "缓存穿透/击穿/雪崩怎么处理？"

### 10.2 一句话答法

> 三级读：本地 Caffeine（60 秒）→ Redis（TTL 带随机抖动）→ DB 回源；写操作**在事务提交后**才删缓存，删完还往 Redis 发一条广播，让其他实例同步清本地缓存；库存这类"必须立刻全局可见"的数据干脆跳过本地缓存，只走 Redis。

### 10.3 代码要点

```java
// litemall-common-cache/src/main/java/com/litemall/cache/CacheService.java:56
/** 本地缓存：Caffeine 60s，挡热点读（跨节点失效由广播通道保证） */
private final Cache<String, String> localCache = Caffeine.newBuilder()
        .maximumSize(1024).expireAfterWrite(Duration.ofSeconds(60)).build();

@param ttlSeconds    Redis 基础 TTL（实际 = ttl + random[0,jitter)）   // 雪崩抖动
@param jitterSeconds 雪崩抖动区间

public <T> T get(...)          // 本地 → Redis → DB
public <T> T getWithLock(...)  // 回源时加分布式锁（防击穿）
public <T> T getShared(...)    // 跳过本地 Caffeine，只走 Redis → DB（库存用）

/** 删缓存（写 DB 后调用）：本机失效 + Redis 删除 + 广播其他节点失效 */
public void del(String key) {
    localCache.invalidate(key);
    stringRedisTemplate.delete(key);
    publish(MSG_KEY + key);        // M8：pub/sub 广播，其他实例清本地
}
```

### 10.4 三个经典问题的答法

| 问题 | 本项目做法 |
|---|---|
| **穿透**（查不存在的数据打穿到 DB） | 空值也缓存，用特殊标记 `::NULL::`，TTL 60 秒（比正常 TTL 短） |
| **击穿**（热点 key 失效瞬间大量请求回源） | `getWithLock`：回源前抢一个短锁（等待 50ms × 重试 3 次），抢不到的直接用旧值/等待；只有拿到锁的去查 DB |
| **雪崩**（大量 key 同时过期） | TTL 加随机抖动：`ttl + random(0, jitter)`，把过期时间打散 |

### 10.5 为什么删除要放在 afterCommit

```java
// litemall-marketing/src/main/java/com/litemall/service/impl/AdServiceImpl.java:188
/**
 * 事务同步激活时注册 afterCommit；无事务上下文（如单测/直调）时立即删。
 */
private void invalidateAdListCache() {
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() { /* 删 redis + 广播 */ }
    });
}
```

如果在事务里删：另一个请求立刻回源，**读到的还是未提交的旧数据**，然后把旧数据写回缓存——事务一提交，缓存里躺着的是旧值，而且没有任何人会再去删它。这个 bug 很隐蔽，只在并发下出现。

### 10.6 追问预判

| 追问 | 答法 |
|---|---|
| "为什么更新时不直接写缓存，而是删？" | 并发写场景下，两个事务的提交顺序和写缓存顺序可能相反，会导致缓存长期是旧值（经典 Cache-Aside 问题）；删除让下一次读回源，最坏是"多一次回源"，不会错 |
| "本地缓存 60 秒，多实例不一致怎么办？" | 广播失效 + 60 秒上限兜底；库存这种不能容忍的，用 `getShared` 直接跳过本地缓存 |
| "Redis 挂了怎么办？" | 读路径降级为直查 DB（`try/catch` 包住缓存调用），写路径只删本地。**不保证性能，但保证可用** |
| "缓存和 DB 会不会双写不一致？" | 会存在极短窗口（删除到回源之间），这是 Cache-Aside 的固有属性；对账类数据（金额）不走缓存 |

## 11. 契约与工程化（容易被忽略但很能加分）

### 11.1 统一响应信封 + "对外恒 200"

```json
{ "code": 200, "msg": "ok", "data": { ... } }
```

**为什么对外接口永远返回 HTTP 200？**

1. 前端只需要判断 `code`，不用同时处理 HTTP 状态码和业务码两套分支；
2. 业务失败（库存不足、券不可用）不是"HTTP 错误"，是**正常的业务结果**；
3. 反过来，`/inner/**` 内部接口**必须保留真实 4xx/5xx**，否则 Feign 客户端会把失败当成功，重试/降级逻辑全部失效。

**细分错误码**放在 `data.errorCode`（两层登记：通用码 + 域内码），HTTP 层只保留 401/403/404/409/429 这几类真·协议层语义。

### 11.2 金额用整数分

DB 里存 `int` 分，Java 里用 `BigDecimal` 但**只在计算时用**，出参统一 `Money.fen(...)` 转分（`Integer`）。
原因：`double` 有精度问题（`0.1 + 0.2 != 0.3`），`BigDecimal` 在前端 JSON 里会被序列化成字符串或浮点，容易踩坑；**整数分是唯一没有歧义的单位**。

### 11.3 ID 字符串化

`Long` 超过 2^53 后，JS 的 `Number` 会丢精度（`9007199254740993` 变 `9007199254740992`）。所以所有 ID 在出参时转成字符串。这也是为什么后来把全库 ID 从 `int` 改成 `bigint`——`int` 自增扛不住数据量，而前端必须按字符串消费。

### 11.4 527 个测试是怎么来的

- 单元测试：纯 Mockito，不打 DB（服务层逻辑、边界、异常分支）；
- 集成测试：`@SpringBootTest` 起上下文（验证 Bean 装配、配置可解析、Mapper 能加载）；
- 端到端：脚本起 9 个服务 + 真实 MySQL/Redis/Nacos，跑业务脚本（下单→支付→售后→退款），断言 HTTP 响应和 DB 数据。

**可以主动说的一句**：单测覆盖率不是目标，**"变异测试"才是**——我改坏过一处排序逻辑（把降序改升序），特意确认测试会红，红不了就说明这个用例是空的。

## 13. 三个真坑（讲故事素材，比概念值钱）

### 坑 1：假绿——测试全过，但线上功能是坏的

> 有一次全量 `mvn verify` 18 个模块全绿，我以为没事。结果联调时发现：接口返回的 `errorCode` 永远是 `null`。
> 查了很久才明白：我把 `litemall-common` 从 jar 改成了 `pom` 聚合模块（拆成 5 个子模块），但 9 个服务的 pom 还是按 `jar` 依赖它。Maven 于是从本地仓库 `~/.m2` 拿了一个**几周前的旧 jar**，里面没有新代码。
> 编译器不报错、测试也能过，因为测试用的也是那个旧 jar。**这是"构建成功"和"代码生效"之间的裂缝**。
> 修法：9 个 pom 都加 `<type>pom</type>`，删掉本地仓库里的陈旧 jar，重新 verify。
>
> 教训：**绿灯只能证明"测试通过"，不能证明"代码被用上了"**。改模块结构后一定要确认依赖解析到的是本地源码，而不是仓库里的旧产物。

### 坑 2：早了 234 毫秒的延时消息，让订单永远不关

见 6.6 节（完整故事）。要点：多源时间不精确 + "不满足条件就 ACK" = 事件永久丢失。修法是**失败路径要能自愈（补投）**，不能假设只触发一次。

### 坑 3：DATETIME 不存毫秒

> 订单的 `expire_time` 是 `LocalDateTime`，Java 侧带纳秒精度，写进 MySQL `DATETIME`（默认精度 0）就被截断到秒。
> 这本身不是 bug，但它和延时消息的秒级取整叠加，就造成了坑 2 里那 234 毫秒的差。
>
> 教训：**跨系统传递时间，要明确精度**。要么统一用 `DATETIME(3)`，要么所有比较都先截断到秒。
