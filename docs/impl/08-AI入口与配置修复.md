为什么不走标准 `pip install -r requirements.txt`：本机直连 PyPI 十分钟无进展，清华镜像报
`ERROR: Could not find a version that satisfies the requirement fastapi>=0.111 (from versions: none)`（镜像不可达）。
`--system-site-packages` 继承 conda 已有版本，实测全部满足 `requirements.txt` 下限：
`fastapi 0.135.1 / uvicorn 0.46.0 / langgraph 1.1.2 / langchain 1.2.12 / langchain-openai 1.1.11 / httpx 0.28.1 / python-dotenv 1.2.1 / pydantic 2.12.5 / redis 8.1.0`。
**代价**：venv 不再隔离于 conda base，conda 升级依赖会连带影响；若要彻底隔离，需在能连通 PyPI 的机器上 `pip install` 后拷贝。

### 2.4 配置降级（不再 500，也不再答非所问）

三处联动，缺一不可：

1. `app/llm.py::get_llm()` — 配了 `ark`/`deepseek` 但缺 Key 时**不抛 RuntimeError**，回落 `MockProvider()` 并只 WARN 一次；新增 `effective_provider()` / `degraded_reason()`。
2. `app/config.py::llm_key_present` + `use_agentic_graph` — **必须看密钥而不是 provider 名字**。只做第 1 步时，`get_llm()` 已降级但编排层仍选 agentic 图，`get_chat_model()` 返回 `None`，`node_agent` 直接回 `FALLBACK_REPLY`，于是每个问题都答「我还没完全理解你的意思」——这是本次实测踩到的真坑。
3. `app/main.py::health()` — 先 `get_chat_model()` 触发一次惰性降级，再读 `effective_provider()`；否则 health 会把「已降级」误报成 `llm_effective_provider=deepseek`。

`/agent/health` 原有 6 个字段一字未改，只追加 `llm_effective_provider`、`llm_degraded_reason`（前端健康判断逻辑不受影响）。

### 2.5 商品搜索关键词兜底

`app/tools/mall_tools.py`：`search_goods` 改为按「整句 → `_extract_keyword` 抽词 → 抽词去空格 → 不带关键词取热门」依次退让。

必须去空格的实测依据：库里商品名是 `素色圆领T恤`（无空格），用户常写 `T 恤`，带空格搜恒 0 条 —— 这也是 R3 验收 24/25 那条 FAIL 的根因。修复后同一句话命中 `o353598T恤 / p353598T恤 / …` 五张卡。

`_match_category` 同步做去空格 + 小写归一，修「T 恤」落不进「服饰」。

### 2.6 会话状态串味（顺带修的真缺陷）

`node_route_intent` 每轮清空 `tool_payload`：

```python
return {"intent": await llm.route_intent(state["message"]), "tool_payload": None}
```

原因：checkpointer 按 `thread_id` 跨轮累积 state，「先问商品 → 再说你好」会让问候也带上上一轮的商品卡片。修复前实测：`你好` 返回 greeting 文案但带 5 张商品卡；修复后 cards 为空。
