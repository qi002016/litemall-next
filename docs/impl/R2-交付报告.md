### 3.3 t11 八步验收发现的缺陷（D-A / D-B / D-C / D-D，均已修复并复跑）

> 全部为**真缺陷**：在真服务 + 真库上可复现，修复后由同一脚本复跑通过。总表见 `docs/evidence/r2-08/R2-八步验收结论.md` §五；编号与 t11 结论文档一致。

**D-A｜`GET /app/goods/brand/list` 不传分页参数直接 500**（阻塞步骤 2）

- **现象**：`GET /app/goods/brand/list`（`CI-34`）不带 `pageNum`/`pageSize` 时返回 `{"code":500,"msg":"系统内部异常"}`，契约规定缺省按 `1`/`20`。
- **根因**：控制器方法用**裸 `int`** 接收这两个查询参数。Spring 对裸基本类型的 `@RequestParam` 视为**必填**，缺参时在参数绑定阶段就抛 `MissingServletRequestParameterException`，早于服务层兜底与统一异常处理，最终转成 500。
- **修法**：改为 `@RequestParam(required = false) String` 接收 + 手工 `parseInt`（空 ⇒ `null` 交服务层落默认；非法整数 ⇒ 400 `PARAM_INVALID`），默认值只在服务层出现一次。
- **证据**：`GoodsController.java:112-120`（`getBrandList`）、`:122-131`（`parseInt`）；回归用例 `litemall-goods/src/test/java/com/litemall/controller/BrandListApiTest.java:35-40`（类注释明写「不传 pageNum/pageSize ⇒ 200，绝不允许原先裸 int 造成的 500」）；t11 复跑步骤 2 全通过。**状态：已修复、已复跑。**

**D-B｜`CI-34` 的 `floorPrice` 返回元浮点而非整数分**（阻塞步骤 2，并影响步骤 1 观感）

- **现象**：`GET /app/goods/brand/list` 返回 `floorPrice: 0.00` / `39.00`（元），契约要求整数分 `0` / `3900`。
- **根因**：出参直接沿用了库里的 `DECIMAL(10,2)` **元**值（等同 Bean 拷贝），漏掉「库元 → 出参分」的边界换算。契约（`08` §1.4）原文一直写「分」，因此这是**实现向契约回正**，不是改契约。
- **修法**：统一 `movePointRight(2)` + `setScale(0, HALF_UP)`，换算只在服务边界发生一次；出参按全仓 Long→字符串 序列化（JSON 里是 `"3900"`，**值是分、不是元**），验收断言按「数值 = 库内元×100 的四舍五入整数」校验、不锁 JSON 类型。
- **证据**：`CatalogSupport.java:135`、`GoodsSupport.java:47`；`BrandListApiTest` 类注释 D-B 条（`39.00` 元 ⇒ `3900`）；t11 复跑通过。**状态：已修复、已复跑。**

**D-C｜新建分类后前台最长 5 分钟看不到（分类树缓存竞态）**（步骤 1 偶发不可见）

- **现象**：后台 `POST /admin/category/create` 返回 200 且库里已有新行，但紧接着 `GET /app/goods/category`（`CI-33`，读 `category:tree`）仍返回旧树，最长持续 300s（缓存 TTL）。
- **根因**：`del(category:tree)` 写在 `@Transactional` 方法**体内**，早于事务提交。此时若有并发读，读者会用**提交前的 REPEATABLE READ 快照**重建缓存——旧树被写回并带上新的 300s TTL，等于「旧快照预热」；写侧随后提交，但缓存已被旧数据占据。
- **修法**：`TransactionSynchronizationManager.isSynchronizationActive()` 时注册 `afterCommit` 再 `del`；无事务上下文时立即 `del` 兜底（否则单测里"看起来生效"、生产才暴露）。失效异常只 `WARN`，不回滚已提交的业务。
- **证据**：`CategoryServiceImpl.java:389-401`（注释即写明「事务未提交时读者会用旧快照重建，前台最长 5 分钟看不到刚提交的分类」）；口径冻结于 `05` §5.20；`08` v11 §1.3 增「缓存与失效」引用块；t11 复跑通过（UI 复跑**未清缓存**，见 §6）。**状态：已修复、已复跑。**

**D-D｜C 端商品详情缺 `brandName`/`categoryName`**（阻塞步骤 2「详情显示品牌」）

- **现象**：`GET /app/goods/detail` 只回 `brandId`/`categoryId`，C 端详情页取不到名称，只能显示「—」。
- **根因**：详情 VO 组装只映射了 id，没有按 id 反查名称；`08` §1.2 的「只增名称字段」此前未实装。
- **修法**：详情组装时按 `categoryId`/`brandId` 反查 `litemall_category.name` / `litemall_brand.name`；**软删或 id 为空 ⇒ `null`**（不返空串，避免「没有品牌」与「品牌已下线」混淆）。
- **证据**：`GoodsServiceImpl.java:359-361`（注释「R2-10 D-D：详情页要展示品牌/分类名称」）、`:388`/`:410`（两个反查方法）、`:569-595`（列表侧批量反查）；t11 复跑步骤 2 通过（`brandName=ACME`、`categoryName=上装`，补证 `docs/evidence/r2-08/t19-postfix-probes.txt`）。**状态：已修复、已复跑。**
