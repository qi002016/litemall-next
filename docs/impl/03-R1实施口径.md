## 1. Q5 订单状态字典（冻结 = 选项「丙」）

### 1.1 结论

**沿用现状 5 个字面量 + 新增 `completed`(501) 与 `canceled`(103)，共 6 个主状态；退款不占主状态，401/402 降为存量只读两态。**

选丙而不选乙（全换原型 7 态）：出参 `status` 是**字符串标识**（P-06 已裁定不改类型），500 行订单/3 个前端/后台筛选全部按字符串判断，换名等于全量破坏；丙只新增 2 个值、一处映射表，且与 `BR-ORD-09` 的 7 栏天然对齐（7 栏是**前端分栏**，不是 7 个主状态——主状态只有 6 个，见 `需求文档.md:226`）。

### 1.4 C 端 7 栏判定（冻结，可直接翻成查询条件）

`tab` ∈ `all`(默认) / `unpaid` / `undelivered` / `shipped` / `unreviewed` / `finished` / `aftersale`。全部基于**本人**（`user_id = 当前用户`），除 `all` 外都不额外排 `user_deleted`（隐藏只影响 `all`，`07` §4.2）。

| `tab` | 判定（`og` = `litemall_order_goods`） |
|---|---|
| `all` | `user_deleted = 0` |
| `unpaid` | `order_status = 101` |
| `undelivered` | `order_status = 102` |
| `shipped` | `order_status = 201` |
| `unreviewed` | `order_status = 301` 且 `EXISTS(og.deleted=0 AND og.refund_status=0 AND og.comment=0)` |
| `finished` | `order_status = 501` **或**（`order_status = 301` 且 `NOT fullyRefunded` 且 `NOT EXISTS(og.deleted=0 AND og.refund_status=0 AND og.comment=0)`） |
| `aftersale` | `EXISTS(aftersale.status IN (0,1,2,3))` **或** `fullyRefunded = true`；**一单可同时出现在本栏与其主状态栏** |

三条必须按本卡落地的细则：

1. **「未评价」的判据是 `og.comment = 0`**（`order_goods.comment` 是三合一列：-1 超期不可评 / 0 可评 / >0 评论 id，见 `OrderGoods.java:63` 与 `07` §1.3）。`comment = -1` 视为**不可评价**，**不参与**"是否全部评价"判定，否则订单永远无法完成。R1 **不写 -1**（写 -1 属〔R2〕评价窗口任务）。
2. **`finished` 必须显式排除 `fullyRefunded`** —— 否则"所有行都退款"会让 `NOT EXISTS(待评价行)` 真空成立，把全退款订单误判成已完成，直接违反 `BR-ORD-09`（`:265`「全部行已退款的订单不进已完成，保持已收货 + 已全额退款标记」）。
3. **`status` 与 `tab` 同传时 `tab` 优先**；`tab` 非法 → `400 PARAM_INVALID`；列表**永不返回 404**（空结果 `total:"0"`、`list:[]`）。

`fullyRefunded` / `refundedAmount` 是**派生值**（`litemall_order` 无此列，实测确认）：`fullyRefunded = NOT EXISTS(og.deleted=0 AND og.refund_status <> 2)`；`refundedAmount = Σ(og.actual_amount × og.refunded_number / og.number)`。**禁止**用已废弃的 `order.refund_amount` 列（`03:426`，停写）。

### 1.5 301 → 501 触发条件（以 `BR-ORD-09` 为准）

**唯一写点**：〔R2〕`CI-36 POST /app/goods/comment/post` 评价落库成功后的同事务内 CAS。

**触发条件（全部满足才跃迁，缺一不跃迁）**：

1. 当前 `order_status = 301`（CAS 条件，`affected = 0` 视为已被并发处理，直接 200 幂等返回，不报错）；
2. 该订单**不存在**「未退款且未评价」的行：`NOT EXISTS(og WHERE og.deleted=0 AND og.refund_status=0 AND og.comment=0)`；
3. **不得**因"所有行都已退款"而跃迁（条件 2 在真空下成立时须再判 `NOT fullyRefunded`）。

**三条禁止**：

- **禁止**把 501 当成"退款完成"用（那是 402 的历史语义，已停写）；
- **禁止**在 501 跃迁时写 `end_time` —— `end_time` 语义是"订单关闭时间"（`03:423`、`07` §6.7 事实更正），只有关单动作写；501 不写 `end_time`、不写 `close_type`；
- **禁止**任何"定时/后台批量把 301 刷成 501"的实现 —— `BR-ORD-05`（`:261`）本期不做自动确认收货，评价触发是唯一来源。

**售后与 501 的关系**：已 501 的订单仍可在 7 天内申请售后（`BR-AS-03` `:295`：已收货/已完成 7 天内两者都可），售后单创建**不改变主状态**（`BR-ORD-08` `:264`），501 不回退。因此 `finished` 栏的判定必须带 `NOT fullyRefunded`，而 `aftersale` 栏可同时命中同一单（§1.4）。

## 2. Q6 存量 401 语义（冻结 = 选项「甲」）

### 2.1 结论

**401 = 退款中、402 = 退款完成，语义原样保留；两者新流程一律停写，只作存量只读展示。不清库、不迁移、不改义。**

不选乙（401 改义为已完成）的理由：`05` Q6 的乙只在"清库重建"前提下成立，而 R1 13 步与 30 分钟回归都在有数据的环境跑，且**生产/联调库不可假设为空**；改义会让"旧的 401 数据"在升级后静默变成"已完成"，这是**语义漂移且不可逆**的高危变更。丙（清库→用乙）被甲吸收：清库属环境操作，不需要契约层支持。

### 2.2 只读兼容的边界（四条硬约束）

1. **不迁移数据**：不写升级脚本把 401→其它值、402→501；不重建订单表。
2. **不清库**：不因 Q6 要求清空 `litemall_order`；种子数据可另造。
3. **不再写入**：R1 起任何路径（`CI-97` 支付回调、`CN-07` 退款、`CX-06` 退役、后台关单）**都不得**写 401/402。唯一的例外是**存量行**被读。
4. **不参与状态机**：401/402 不进入任何"允许/禁止某动作"的判定（现状 `adminRefund` 里"101/103/402 拒绝、401 幂等"的逻辑（`OrderServiceImpl.java:470/480`）随 `CX-02/CX-03` 一起删除，不迁移到新售后台）。

### 2.3 C 端文案与 402 字符串纠正

| 库内码 | 出参 `status` | `statusText` | C 端展示 |
|---|---|---|---|
| 401 | `refund` | 退款中 | 订单行打「退款中」标签；出现在「售后」栏（若仍有未完结售后单） |
| 402 | `refunded` | 已退款 | 整单打「已全额退款」标记；出现在「售后」栏 |

**402 的字符串现状缺陷（必须修）**：`OrderServiceImpl.java:716-731` 的 `statusText` 反向映射把 **402 折叠成字符串 `refund`**（`:727-728` 注释"402 与 401 对外同样呈现为 refund"）。后果是后台与 C 端**无法区分退款中与退款完成**。本卡裁定：**402 出参 `status = refunded`、`statusText = 已退款`**，与 `07` §1.1 表一致。

- 这属于"实现向契约靠拢"，不是契约变更（`07` §1.1 早已列 `refunded`）；
- 影响面仅存量 402 行（R1 起不再产生），且两套前端在 R1 都重写，无存量前端兼容负担；
- 同时 `parseStatus`（`:701-713`）必须补 `completed`(501)、`canceled`(103)、`refunded`(402)——现状只认 5 个词（`unpaid`/`undelivered`/`shipped`/`confirmed`/`refund`），其余落 `default → null`；而 `adminListOrders`（`:404-408`）是 `.eq(statusCode != null, Order::getOrderStatus, statusCode)`，**null 等于"不筛"** ⇒ 现状在后台按「已关闭」筛选会**静默返回全部订单**（不报错、结果错），按 501 筛选同理；`statusText` 对 501 返回 `"unknown"`（`:734`）。这是 R1 必修缺陷，不是新特性。

### 2.4 后台筛选口径（`CI-26` / `CI-99`）

`status` 入参**保持字符串**（`06` §4：存量已是字符串标识的字段不改类型），值域 = §1.2 的 6 个主状态 + §2.3 的 2 个存量态，**多值逗号分隔**：

| `status` 取值 | 映射 | 说明 |
|---|---|---|
| `unpaid` / `undelivered` / `shipped` / `confirmed` / `completed` / `canceled` | 101 / 102 / 201 / 301 / 501 / 103 | 主状态，正常筛 |
| `refund` | 401 | **只命中 401**，不合并 402 |
| `refunded` | 402 | **只命中 402** |

两条口径：

1. **`refund` 不再"代表所有退款态"**。现状后台按 `refund` 只查到 401（`parseStatus` 返回 401），402 行**既筛不出也很少出现**——本卡把两者拆开，语义清晰且不改变既有取值的含义。
2 派生态筛选走**独立入参**，不塞进 `status`：`fullyRefunded`(bool)、`aftersaleStatus`(售后 8 态多值)（`07` §3.1）。若前端需要"所有退款相关订单"，用 `status=refund,refunded` 多值或 `fullyRefunded=true` 组合，**不得**新增 `status=refund_all` 之类假值。

## 3. Q9 退货地址来源（冻结 = 选项「① 全局配置」）

### 3.1 结论

**唯一取值 = 全局配置项 `hm.aftersale.returnAddress`，定义在 `litemall-common-core/src/main/resources/common.yaml`（9 个服务共享），默认空串，由环境变量 `HM_AFTERSALE_RETURN_ADDRESS` 注入。不加表、不加列、售后单不存快照。**

为什么不是②复用 `address` 行：`address` 是**用户收货地址**表，语义是"买家地址"，塞一条"商家仓库地址"需要伪造 `user_id`、且用户可删可改可设默认，会污染 `UserAddressController` 的 5 个端点与"默认地址唯一"约束。为什么不是③新增配置表：R1 只需要一个字符串，加表意味着加 CD、加迁移、加 CRUD、加权限，收益为零。

### 3.2 取值与读取规则（唯一）

| 项 | 值 |
|---|---|
| key | `hm.aftersale.returnAddress`（**全仓唯一**，禁止各服务自定义别名或写死常量） |
| 位置 | `litemall-common-core/src/main/resources/common.yaml` 新增 `hm.aftersale.returnAddress: ${HM_AFTERSALE_RETURN_ADDRESS:}`（现状该文件**无 `hm.*` 业务段**，实测） |
| 读取方 | **order 服务**（`CN-03` 同意退货 / `CN-16` 详情 / `CN-02` 后台详情出参）只此一处读；admin 服务**不读**（admin 是薄转发层，只透传 `CN-03` 的可选入参） |
| 注入方式 | `@Value("${hm.aftersale.returnAddress:}")`（带默认空串，缺失不 fail-fast——与其他 `hm.*` 口令类配置区分） |
| 覆盖规则 | `CN-03` 入参 `returnAddress`（可选，≤255）**仅覆盖本次响应**：不回写配置、不落 `aftersale` 表、不影响同单后续读取 |
| 快照 | **不存**。`aftersale` 表不加地址列（`03` `CD-07` 的 `return_address` 仍保持"SQL 已注释、不计入 35 列"） |

### 3.3 缺省时的行为（`CN-03` 的 400 分支）

- `type = 2`（退货退款）**且**配置为空 **且** 入参未给 `returnAddress` → **400 `PARAM_INVALID`**，`msg`「未配置退货地址，请先在系统配置中设置」；
- `type = 1`（仅退款）→ **不需要**地址，配置为空也照常成功，出参不带 `returnAddress`；
- `CN-16` / `CN-02` 详情出参：仅 `type=2` 且（配置或审批时留有值）时给 `returnAddress`，否则 `null`（`07` §4.3/§4.8 已定）。

> 注意：`CN-03` 的 `returnDeadline` 仍恒给（`approve 时间 + 7 天`，写 `aftersale.return_deadline`），与地址是否有值**无关**——别把两个字段的成败绑在一起。

## 4. 错误码对齐

### 4.1 三层结构（冻结）

```
HTTP 状态码   → 对外端点恒 200（网关拒绝除外，见 4.2）
Result.code   → 200 / 400 / 401 / 403 / 404 / 409 / 429 / 500（06 §1.2）
Result.msg    → 人可读中文句，前端不得做字符串匹配
Result.data   → 成功：业务对象；失败：null 或 {"errorCode": "XXX"}
```

**`data` 两形态裁定**（关闭 `06` §1.1「失败 `data=null`」与 §1.2.1「细分走 `data.errorCode`」的字面冲突）：失败时 `data` **只允许** `null`（无细分码，如裸 401/403/500）或**恰好一个键** `{"errorCode":"..."}`；**禁止**在失败 `data` 里塞 message/detail/traceId 等额外键，也**禁止**把 `errorCode` 提升为 `Result` 顶层字段（那会让 06 §1.2.1 与两套前端同时失效）。

`errorCode` 的用途边界（`06` §1.2.1 原文）：**只用于前端差异化文案，不参与分支**；**不得只给 errorCode 而省 `msg`**。

### 4.2 公共层改造（现状缺陷，R1 必须先修）

**实测缺陷**：`litemall-common-web/src/main/java/com/litemall/advice/CommonExceptionAdvice.java` 的 `processResponse` 用 `ResponseEntity.status(e.getCode()).body(...)` —— **异常路径的 HTTP 状态 = 400/401/403/500**，与 `06` §1.1「HTTP 恒 200（现状如此）」直接不符（文档这句是错的）。且现状**没有 404/409 的异常类型**（`litemall-common-core/.../exception/` 只有 `BadRequest`/`Unauthorized`/`Forbidden`/`BizIllegal`/`Db`/`Common`）。

冻结三条改造（**归属 R1-02 首批提交，其他任务只消费、不得各改各的**）：

1. **对外端点**（`/app/**`、`/admin/**`）：异常响应改 `ResponseEntity.ok(...)` → **HTTP 恒 200**，body 携带真实 `code`。前端「只判 code」的前提由此成立。
2. **对内端点**（`/inner/**`）：**保留非 200 HTTP 状态**。理由：`/inner/**` 返回裸类型（`void`/DTO），若也返回 HTTP 200，Feign 调用方（如 order 调 goods `deduct`）**无法感知失败**，会把"库存不足"当成功——这是资损级风险。判定方式：按请求 URI 前缀 `/inner/` 分流（`WebUtils.getRequest()` 现成可用）。
3. **网关鉴权拒绝**（如 C 端 token 访问 `/admin/**`）由 gateway 的 WebFlux 安全链直接回 **HTTP 401/403**，不经 advice、不受第 1 条约束。**两套前端必须同时处理** `res.code===401` 与 HTTP 401/403 两种入口（现状 `mobile-web/src/utils/request.js:32-56`、`admin-web/src/utils/request.js:25-46` 已是双路，R1-06/07 **保留该双路**，不得简化成只判 `code`）。

配套：新增 `NotFoundException`(404) / `ConflictException`(409) 两个异常类（放 `litemall-common-core/.../exception/`，与现有 4 个同级），并提供带 `errorCode` 的构造入口，使 advice 能输出 §4.1 的 `data` 形态。

### 4.5 禁止项（评审否决清单）

1. **不得自造 `XXX_INVALID`** —— 参数类一律 `PARAM_INVALID`（`08` §11 已把 9 个参数标签并入：`PRICE_ILLEGAL`/`SKU_REQUIRED`/`SKU_COMBO_DUPLICATED`/`CATEGORY_NOT_LEAF`/`CATEGORY_LEVEL_EXCEEDED`/`AD_LINK_REQUIRED`/`AD_LINK_FORBIDDEN`/`AD_TIME_ILLEGAL`/`COUPON_AMOUNT_ILLEGAL`）。
2. **不得把 `RESTOCK_PENDING` 当对外失败码** —— 钱已退、库存未回补是**部分完成**：`200` + `status=refunding` + `restockPending:true` + `restockStatus=2`；该词只写日志/`data.reason`。
3. **不得只给 `errorCode` 不给 `msg`**；**不得**让 `errorCode` 参与服务端分支。
4. **不得**在 `/inner/**` 返回 `Result` 包装或 `data.errorCode`（裸类型 + HTTP 状态码，`08` §11）。
5. **不得**给列表端点返回 404（空结果 `total:"0"`）；**不得**在详情类端点用 403 泄露存在性（他人资源一律 404，写操作类才 403——P-13 的分界线）。
6. **不得**改 `code` 的既有语义（401≠未付款、403≠已关闭；业务态一律走 `errorCode`+`msg`）。

### 4.6 P-31 冻结（实扣失败）

`CI-97` 收到支付成功回调后调 goods 实扣，若扣减失败（库存不足/异常）：**返回 `200` + `deducted:false` + `shortage:[{productId, shortfall}]`，订单**保持 101 未付款**，写异常日志 + 后台告警，**不自动退款、不置 102**。**禁止**用 409 表达（那会让 pay 侧重试，造成二次扣减语义混乱）。

> 该处置是 `07` §8.2 的"待确认默认值"，本卡冻结为最终值。若要改为"自动退款"，必须先定义资金补偿与对账规则（涉及 pay↔order 二次动钱），属 R2+ 议题，R1 不得擅自实现。

### 4.7 08 域四个开放项冻结（R1 会碰到的）

| 项 | 冻结结论 |
|---|---|
| `08` **D-10**（release 幂等入参） | `CI-43`/`CI-45` **入参只增可选 `orderGoodsId`**（批量走 `items[].orderGoodsId`）；缺省 → 旧行为、无幂等；order 侧 `restock_status` CAS 0→1 成功后才调，goods **不写** `restock_status`、不感知售后（P-03/DR-18） |
| `08` **D-22**（`/inner/**` 错误表达） | 404 用 `RESOURCE_NOT_FOUND` 异常；"库存不足"用 400 + **固定 msg「库存不足」**（沿用现状文案，调用方按 `code` 区分，不解析文案） |
| `08` **D-24**（deduct 出参） | `CI-42` **出参不变**（`void`/`boolean`，失败抛 400）；`CI-44`（批量）出参改 `DeductBatchResultDTO{deducted:boolean, items:[{productId, deducted, shortage}]}`，供 `CI-97` 填 `deducted`/`shortage[]`；`CI-43/45` 同理改 `ReleasedBatchResultDTO`（重复回补**不报错**，`released:false` 即可） |
| `08` **D-14**（券状态字典） | `coupon.status`：0 正常 / 1 停用 / 2 已过期；`coupon_user.status`：0 未使用 / 1 已使用 / 2 已过期；`CN-19` 只返回 `coupon.status=0` 且 `coupon_user.status=0` 且未过期者 |

> 注：`/inner/**` 属服务间接口，**不受 `06` §7「只增不删」约束**（该约束针对 84 个对外端点）；但 R1 内改出参必须**同批**改调用方（`CI-44`→`CI-97`、`CI-43/45`→order 回补），由 §6 的任务边界保证同批。
