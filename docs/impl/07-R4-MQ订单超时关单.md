# R4-MQ：订单超时自动关单（RocketMQ 延时消息）

> 取证时点：2026-11-07。本文只记录**已在本机真实跑通**的行为与证据；未验证的内容明确标注。

## 1. 为什么做

改造前：`OrderServiceImpl` 在提交订单时写入 `expire_time = now + 30min`，`closeUnpaidOrder(order, CLOSE_TIMEOUT, …)` 也已实现，但**没有任何触发器**调用它——`adminCloseExpired` 只挂在 `/inner/order/admin/close-expired` 上，需要外部调度来打。结果是未付款订单永不关闭，`order_status=101` 会一直挂着（锁量由 `order_status=101` 派生，长期不关单会持续占用可售量）。

本次把它补成一条真实可用的闭环：**下单事务提交后投递 RocketMQ 延时消息 → 消息到期消费 → 复用既有 `closeUnpaidOrder` 关单**，并保留 `adminCloseExpired` 兜底扫描。

## 2. 链路

```
POST /app/order/submit
  └─ OrderServiceImpl#submitOrder（@GlobalTransactional）
       ├─ saveOrder(order) → expire_time = now + hm.order.expire-minutes
       └─ OrderTimeoutPublisher#publishAfterCommit(orderId, expireTime)
              └─ TransactionSynchronization.afterCommit → syncSend(topic, msg, 3000ms, delayLevel)
                                                     ↓
                          RocketMQ topic: litemall-order-timeout（17 级延时）
                                                     ↓
OrderTimeoutConsumer#onMessage（consumerGroup=litemall-order-timeout-consumer）
  └─ OrderServiceImpl#closeExpiredOrder(orderId)（@GlobalTransactional）
       ├─ 订单不存在 / 非 101 → ACK，返回 false（重复投递的常态）
       ├─ 尚未到 expireTime  → **补投一条更短延时的消息**，返回 false
       ├─ CAS 关单成功        → close_type=2、写 order_log(action=order:close-expired)
       └─ 并发被抢（409）     → ACK，返回 false，不重试
```

兜底：`OrderTimeoutFallbackScheduler` 每 5 分钟调一次 `adminCloseExpired(200, false)`（`hm.order.timeout-scan.enabled=false` 可关）。

## 4. 关键设计点（面试/复盘口径）

1. **afterCommit 而非事务内投递**：事务回滚就不该有关单消息；否则会提前关掉一张根本不存在的订单。`publishAfterCommit` 用 `TransactionSynchronizationManager` 注册回调，无事务时立即发送。
2. **幂等**：消费端先按 `id + order_status=101` 选行，再走 `closeUnpaidOrder` 的 CAS（`UPDATE … WHERE order_status=101`）。重复消息、消息与兜底扫描并发，都只会有一个成功；CAS 失败（`ConflictException`）视为"已被别人处理"，**不重试**。
3. **提前到达必须自我纠偏（本次实测踩到）**：延时等级按秒取整、`expire_time` 是 `DATETIME` 秒级存储、Broker 与业务时钟有偏差，消息可能比 `expire_time` **早几百毫秒**到达。旧写法直接 ACK 会导致这张订单永远关不掉（见 §5 的 998038）。现在改为"提前到达就补投一条更短延时的消息"，`remain < 1s` 时等级为 1s，因此最多再跳一次就收敛、不会无限循环。
4. **发送失败不阻断下单**：`syncSend` 异常只 `log.error`；下单成功与否不依赖 MQ 可用性，缺口由兜底扫描兜住。`hm.order.timeout-mq.enabled=false` 可整体退化为纯扫描。
5. **延时等级上限**：RocketMQ 5.x 默认 18 级（最长 2h），`expire-minutes` 大于 2h 时 `delayLevelOf` 取 18，等于最多提前 2h 投递 —— 由第 3 点的补投逻辑兜住，不会漏关。

## 5. 实测证据（真实 broker：`192.168.96.129:9876`，本机 9 服务全起）

启动参数：`HM_ORDER_EXPIRE_MINUTES=1`（缩短等待）、`HM_ORDER_TIMEOUT_SCAN_ENABLED=false`（排除兜底扫描干扰，确保关单只能来自 MQ）。

| 订单 | 结果 | 证据 |
| --- | --- | --- |
| 998037 | `101 → 103` | `[MQ] 订单超时延时消息已投递：orderId=998037, delayLevel=5, remainSeconds=59` → `[MQ] 超时关单消息消费完成：orderId=998037, closed=true`；`order_log` 写入 `order:close-expired / 超时未支付，MQ 延时消息自动关闭` |
| 998038 | **未关闭（暴露缺陷）** | 消息 14:08:25.766 到达，`expire_time=14:08:26` → 命中"尚未到期"分支直接 ACK ⇒ 订单停在 101 |
| 998039（修复后） | `101 → canceled` | 第一次消费 `closed=false`（提前到达）→ 自动补投 → 1s 后第二次消费 `closed=true`，`/app/order/detail` 返回 `status=canceled / statusText=已关闭` |

`998038` 就是第 3 点的由来；修复后 `998039` 在真机上跑出了"提前到达 → 补投 → 关单"的完整路径。

## 6. 测试

- `OrderTimeoutPublisherTest`（7 例）：无事务立即投、事务提交后投一次、回滚不投、发送异常被吞、开关关闭不取模板、null 入参静默、`delayLevelOf` 边界（0→1、2→2、60→5、61→6、1800→16、99999→18）。
- `OrderTimeoutConsumerTest`（3 例）：转交 service、空体丢弃、异常传播。
- `OrderTimeoutCloseTest`（6 例）：到期关单（含 `close_type=2` 与日志 action）、**提前到达补投**、订单不存在、CAS 被抢、券回退失败不阻断、null id。
- 既有 6 个订单测试类补 `OrderTimeoutPublisher` mock 与构造器参数。
- `litemall-order` 模块 `mvn -o verify`：**178 例全绿**（改造前 152 例）。

## 7. 未验证边界

- 只在**单实例**上验证；消费者是 CLUSTERING 模式，多实例同样消费同一 topic，但"同一订单两条消息并发"仍靠 CAS 兜底，未做压测。
- 未验证 broker 宕机/重启后延时消息的补偿行为（依赖 RocketMQ 自身）。
- 未验证死信队列告警（消费连续失败 16 次进 `%DLQ%litemall-order-timeout-consumer`），项目内目前无死信监控。
- 兜底扫描默认开启（5 分钟一次），与 MQ 双保险；本机验收时用手工关闭来证明关单确实来自 MQ。
