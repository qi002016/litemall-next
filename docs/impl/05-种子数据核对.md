# R2 演示种子数据核对（R2-07 / t8）

- 脚本：`db/seed/r2-demo-seed.sql`（324 行，纯 DML，不含任何 DDL）
- 口径：需求文档 8-Q21 × `docs/impl/05-R2实施口径.md` §8.1 × CI-08 报表 SQL（§2.1.3）
- 执行时间：2026-11-01 19:39（本机 `127.0.0.1:3306/litemall`，MySQL 8.0.46）
- 执行方式：
  ```bash
  mysql -h127.0.0.1 -P3306 -uroot -p --default-character-set=utf8mb4 litemall < db/seed/r2-demo-seed.sql
  ```
  中文列值必须带 `--default-character-set=utf8mb4`，否则客户端按 GBK 解析报 `ERROR 1115`。
- 可重复执行：脚本开头按**精确 ID 列表** `DELETE`（19 张表，`WHERE id IN (…)`），随后单事务插入；用精确 ID 而非 `BETWEEN` 宽段，是因为本机库已有其他 cohort 在相邻号段写入数据（`admin` 991203+、`log` 999109+），宽段 `DELETE` 会误删正在验收使用的行。幂等证据两份：①`BETWEEN` 版本连跑三次结果逐行一致（订单 35 / 订单行 45 / 评价 17 / 售后 8 / 退款 3 / 商品 12）；②改为精确 ID 后做「同一事务内把整份脚本连跑两遍再 `ROLLBACK`」的干跑——第二遍必须先删掉第一遍插入的行才可能不撞唯一键，实际退出码 0 且回滚后行数不变。

## 4. CI-08 数字的两种视角

核对 10 是**全库**口径（报表接口真实的取数范围），因此混入了 R1 历史订单（id 1–54，含 102/103/301 噪音）与**其他任务并发灌入的演示数据**（例如 `litemall_refund` 里 id 1–11 由其他 cohort 在 17:29–18:43 写入、关联 order 28–49）。

> **验收判据**：第 6/7 步验的是「工作台数字与同期 SQL 合计一致」——**一致性**检验，不是绝对值检验。验收时以检查那一刻的实时 SQL 为准，工作台与 SQL 用同一时间窗、同一统计域（全库），两边相等即通过。下表的 ID 段口径仅作**补充证据**，用于解释数字差异的来源（R1 历史数据 + 其他 cohort 并发写入），不作为判据。

## 6. 账号与口令

| 账号 | 表 | 口令 | 状态 |
| --- | --- | --- | --- |
| `r2demo_admin`（991201） | `litemall_admin` | `admin123`（复用 R1 admin 哈希，60 字符） | `status=1` 启用，实测 `POST /admin/auth/login` → `code=200` + token |
| `r2demo_disabled`（991202） | `litemall_admin` | 同上 | `status=0` 禁用，实测登录 → `code=403` + `ADMIN_DISABLED`（**不是** `LOGIN_FAILED`） |
| `r2demo_buyer1/2/3`（991101–991103） | `litemall_user` | 复用 R1 买家哈希，均 60 字符（实库 `LENGTH(password)=60`） | `status=0` 可用 |

bcrypt 串长度是**必须校验**的量：`admin123` 账号的哈希若被截断 1 个字符，登录端只会返回 `LOGIN_FAILED`，看起来像"口令错"而不是"数据坏"。脚本生成器已内置 `assert len(PWD_USER)==len(PWD_ADMIN)==60`。

## 7. 已知事项

1. 脚本时间全部是相对 `NOW()` 的表达式，因此**每次重跑都会平移时间**；`refund_time` 落今日的那条（998601）永远保持"今日"语义，便于反复验收第 6 步 `today` 周期。
2. 分类/品牌 4 组、商品 12 个均为自有命名，不与验收第 1 步要新建的「服饰」「上装」「ACME」冲突。
3. `litemall_goods_specification` 的取值 id（993201–993216）同时被 `goods_product.spec_value_ids` 引用；全库无外键，脚本仍按「先商品行、后规格取值」的顺序 `DELETE`，保证重跑不残留悬挂引用。
4. 订单 `comments` 列存「未评价行数」：501 的 5 单全部为 0（已评价完）；301 中 998018=1、998019=2，其余为 0。已实库校验一致。
## 8. 缺陷记录：bcrypt 哈希截断导致演示账号不可登录（已修）

| 项 | 内容 |
| --- | --- |
| 现象 | `r2demo_admin` / `r2demo_disabled` 调用 `POST /admin/auth/login` 一律 `401` + `LOGIN_FAILED`，看起来像「口令错」，实际是数据坏 |
| 定位 | `SELECT LENGTH(password) FROM litemall_admin WHERE id IN (991201,991202)` → **59**，而 bcrypt 串必须 60；同一时刻 `admin123`（id=1）为 60 且可登录 |
| 根因 | 种子里的哈希常量被写错：正确串中段为 `…L4lY0cQ**HeqD**gsbdTylBpu`，种子写成 `…L4lY0cQ**HeQ**gsbdTylBpu`（`qD` 变成大写 `Q`，净少 1 字符），bcrypt 比对必然失败 |
| 修复 | `db/seed/r2-demo-seed.sql` 两个账号行改用完整的 60 字符哈希；生成器加 `assert len(PWD_USER)==len(PWD_ADMIN)==60` 防止再次截断 |
| 影响面 | 全库 `SELECT COUNT(*) FROM litemall_admin WHERE deleted=0 AND LENGTH(password)<>60` → 修前 **2**、修后 **0**；`litemall_user` 三个种子买家账号修前即为 60，未受影响 |

### 8.3 修复方式与对运行中数据的影响

修复**没有重跑整份脚本**（验收正在使用库内数据），只对两行做定点 `UPDATE litemall_admin SET password=… WHERE id IN (991201,991202)`。

同时把脚本的清理方式从「按 `BETWEEN` 宽段 DELETE」改为「按**精确 ID 列表** `WHERE id IN (…)` DELETE」：本机库已有其他 cohort 在相邻号段写入（`admin` 991203–991207、`log` 999109+），宽段清理会误删这些行。改后做了两次无副作用干跑，均退出码 0 且回滚后状态不变（订单 35、评价 17、`admin` 12 行、两个演示账号哈希仍为 60 字符）：

1. 把 `COMMIT` 换成 `ROLLBACK` 跑整份脚本 —— 证明所有 INSERT 可通过唯一约束；
2. 同一事务内把整份脚本（去掉 `COMMIT`）连跑两遍再 `ROLLBACK` —— 第二遍必须先删掉第一遍插入的行，证明清理逻辑真的覆盖到自己插入的全部 ID（幂等）。

两条干跑都不会写入运行中库内的任何行，因此不影响 qa-verify 正在跑的八步验收。
