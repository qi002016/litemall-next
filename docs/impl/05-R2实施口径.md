## 1. 公共口径（R2 增量与重申）

### 1.1 信封与三层结构

沿用 R1 §4.1，不重复。R2 只重申三条：

1. 对外 HTTP **恒 200**（**v9 补注 · 鉴权层例外**：`AdminAuthFilter` / 网关过滤器在进 Controller 之前直接写真实 `401`/`403`，二分法见 `06` §1.1.1、错误码见 `07` §1.3；**业务层**才恒 200），前端只判 `Result.code`；`/inner/**` 保留非 200 HTTP（Feign 靠它感知失败）。
2. 失败时 `data` **只允许** `null` 或恰好一个键 `{"errorCode":"XXX"}`。
3. `msg` 是中文短句，不承载逻辑；`errorCode` 大写下划线，全局唯一，须在 07/08 §11 登记。

**本卡登记的 3 个显式例外（仅此 3 个，不得推广）**：

| 例外 | 端点 | 形态 | 理由 |
|---|---|---|---|
| E-1 | CI-54 领取券（失败且属四态之一） | `code=400` + `data={"result":"already_received"|"sold_out"|"disabled","message":"…"}`（`couponUser` 省略） | 03 §5.2 明写「旧 `code/msg` 保留」，且需求 BR-CP-02 要求四态可区分；R1 §4.1 的 `data` 单键形态容纳不下 `result` |
| E-2 | CI-08 单指标失败 | `code=200` + 该指标字段为 `null` + `data.unavailable[]` 含字段名 | 08 §7.2「单指标失败不影响其他」，需求 §5.13 异常行 |
| E-3 | CN-31 目标态幂等 | `code=200` + 当前态（affected=0 且已等于目标态） | 08 §5.6；避免把幂等重复提交误报 409 |

### 1.2 错误码与 `errorCode` 使用规则

- HTTP/业务码集合（R2 实际用到）：`200`、`400`、`401`、`403`、`404`、`409`、`429`、`500`。**不引入 4xxxx 段**。
- `400` 兜底一律 `PARAM_INVALID`；各域**不得**自造 `XXX_INVALID`。
- **已并入 `PARAM_INVALID`、不产生新码位的标签**（08 §11.3，实现只进 `msg`）：`PRICE_ILLEGAL`、`SKU_REQUIRED`、`SKU_COMBO_DUPLICATED`、`CATEGORY_NOT_LEAF`、**`CATEGORY_LEVEL_EXCEEDED`**、`AD_LINK_REQUIRED`、`AD_LINK_FORBIDDEN`、`AD_TIME_ILLEGAL`、`COUPON_AMOUNT_ILLEGAL`。
  - 【裁定】CN-22「形成三级分类」→ **`400 PARAM_INVALID` + `msg`「分类最多两级」**，**不返回** `CATEGORY_LEVEL_EXCEEDED`（08 CN-22 正文与 §11.3 冲突，以 §11.3 为准）。
- 域内码**只能**用 §1.3 表内的字面量；R2 不需要新增任何码位（08 §11 已含全部 R2 码）。

### 1.4 分页、筛选、排序

- 分页入参 `pageNum`（默认 1）/`pageSize`（默认 20，上限 100，超出按 100）；出参 `PageVO{total,pages,list}`，`total`/`pages` 为**字符串**。
- 筛选：多值逗号分隔（`status=0,1`、`star=1,2,3`）；区间用 `xxxMin`/`xxxMax`（CI-31 的 `minP`/`maxP` 为 08 已定名，保留）；关键词统一 `keyword`；日期区间 `dateFrom`/`dateTo`，格式 `yyyy-MM-dd HH:mm:ss`。
- 排序：`sortBy` 必须白名单，非白名单**忽略落默认**（06 §3「忽略不报错」），不返回 400。

| 端点 | 默认排序 | `sortBy` 白名单 |
|---|---|---|
| CN-21 分类树 | `sort_order ASC, id ASC`（树内同层） | 不支持（全量树，不分页） |
| CN-25 品牌列表 | `sort_order ASC, id ASC` | `sortOrder`、`addTime`、`name` |
| CN-29 评价列表 | `add_time DESC, id DESC` | 不支持（固定倒序） |
| CN-34 公告列表 | `add_time DESC, id DESC` | 不支持（固定倒序） |
| CI-13 日志列表 | `add_time DESC, id DESC` | 不支持（固定倒序；**登记为 06 §3 的例外**，日志必须最新在前） |
| CI-31 商品列表 | 综合序（`id DESC` 兜底） | `price_asc`、`price_desc`、`new`（参数名 `sort`，沿用 08） |

- **翻页稳定性**（BR-SEARCH-06）：所有分页 SQL 必须带确定的次序键（CI-31 用 `id DESC` 作隐含次序），保证同一查询翻页不重不漏。

### 1.5 字段约定

1. **金额一律整数分**：入参分、出参分。库内 `DECIMAL(10,2)` 元，只在服务边界换算（`movePointRight(2)` / `movePointLeft(2)`），字段名不加 `Cent` 后缀。
2. **ID 一律 JSON 字符串**（BIGINT → string）：`id`/`pid`/`categoryId`/`brandId`/`goodsId`/`orderId`/`orderGoodsId`/`commentId`/`userId`/`targetId`/`adminId`/`couponId`。入参接受字符串或数字（Jackson 按 `Long` 反序列化），出参统一字符串。
3. **时间** `yyyy-MM-dd HH:mm:ss`（`Asia/Shanghai`）。
4. **布尔** `true`/`false`（库 `TINYINT(1)`）。
5. **枚举**用数值码 + `xxxText`；**存量字符串枚举不改类型，只追加 `xxxText`**（06 §4）。R2 涉及的枚举见 §1.5.1。
6. 空值：数组永远 `[]`（不返回 `null`）；超长直接 400 拒绝，**不截断**。

### 1.6 时间与统计期口径

- 时区 `Asia/Shanghai`；统计期按**自然日**：`[期初 00:00:00, 次日 00:00:00)`，实现用 `>= start AND < end`（**不用 `BETWEEN`，避免 23:59:59.999 漏数**）。
- `today` = 今日；`7d` = **含今日**往前 7 个自然日；`30d` = 含今日往前 30 个自然日。`trend` 长度分别 1 / 7 / 30，区间内无单日期**补 0**。
- GMV / 订单数归期 = `litemall_order.pay_time`。
- 退款金额 / 退款单数归期 = `litemall_refund.refund_time`（**与退款率分子同源**，08 §7.3）。
- `waitShipCount` / `pendingAftersaleCount` 是**当前存量**，不随 `period` 变化。

### 1.7 表写点归属（R2 红线：一表只有一个写服务）

| 表 | 唯一写服务 | R2 相关读方 |
|---|---|---|
| `litemall_category`、`litemall_brand`、`litemall_comment` | **goods** | admin（经 Feign 转发） |
| `litemall_notice` | **marketing** | admin（经 Feign 转发） |
| `litemall_admin`、`litemall_log` | **admin** | — |
| `litemall_order`、`litemall_order_goods`、`litemall_aftersale` | **order** | admin（Feign）、goods（只经 `CN-IN-01`/`CN-IN-08`） |
| `litemall_refund` | **pay** | order（**只读**，R1 已有先例：`AftersaleMapper.selectRefundBrief` 直读 `litemall_refund`） |
| `litemall_coupon`、`litemall_coupon_user` | **marketing** | — |

- 单库部署（所有服务同 `litemall` 库，`common.yaml` 共用一个 `HM_DB_NAME`），**只读跨域 join 允许且已有先例**；**写跨域一律禁止**（除 §2.3 的 `CN-IN-08` 明确由 order 写）。
- 商品域 `CommentServiceImpl` **不得**直写 `litemall_order_goods.comment` / `litemall_order.order_status`（写权在 order）。这是 §2.3 设计 `CN-IN-08` 的唯一原因。

### 1.8 对内端点通用规则

- 鉴权 `X-Internal-Token`（`FeignInnerConfig` 统一注入）；网关**不路由** `/inner/**`；无用户身份（不得从 body 取 `userId`/`adminId`）。
- **裸类型返回，不进 `Result`**（`PageVO<T>`、`T`、`void` 直接返回）。
- 失败保留非 200 HTTP：`404`（`NotFoundException`）、`409`（`ConflictException`）、`400`（`BadRequestException`）。**调用方必须处理 `FeignException` 的 400/404/409**，不得让其穿透成 500。
- 转发型对内端点（分类/品牌/评价/公告）：**契约字段与对外端点完全一致**，admin/marketing 侧只做鉴权 + 转发 + 日志 + 组装，不做字段加工。

#### 2.1.3 SQL 口径（冻结，逐字照此实现；金额在服务边界 `movePointRight(2)`）

时间参数（Java 侧按 §1.6 算好）：`#{start}`、`#{end}`（`end` = 次日 `00:00:00`）。

**SQL-1 GMV + 订单数**

```sql
SELECT COUNT(*)                              AS orderCount,
       COALESCE(SUM(o.actual_price), 0)      AS gmvYuan
  FROM litemall_order o
 WHERE o.deleted = 0
   AND o.order_status NOT IN (101, 103)
   AND o.pay_time >= #{start} AND o.pay_time < #{end};
```

**SQL-2 退款完成数 + 金额**

```sql
SELECT COUNT(DISTINCT r.aftersale_id)        AS refundCount,
       COALESCE(SUM(r.amount), 0)            AS refundYuan
  FROM litemall_refund r
 WHERE r.deleted = 0
   AND r.status = 1
   AND r.refund_time >= #{start} AND r.refund_time < #{end};
```

> `COUNT(DISTINCT r.aftersale_id)`：`BR-AS-23` 一笔售后一次退款，DISTINCT 防脏数据重复计数；`aftersale_id IS NULL` 的历史行不计入（§0.4 已声明）。

**SQL-3 热销 Top5**

```sql
SELECT og.goods_id            AS goodsId,
       MAX(og.goods_name)     AS goodsName,
       SUM(og.number)         AS quantity,
       SUM(og.actual_amount)  AS amountYuan
  FROM litemall_order_goods og
  JOIN litemall_order o ON o.id = og.order_id AND o.deleted = 0
 WHERE og.deleted = 0
   AND o.order_status NOT IN (101, 103)
   AND o.pay_time >= #{start} AND o.pay_time < #{end}
 GROUP BY og.goods_id
 ORDER BY quantity DESC, amountYuan DESC, goodsId ASC
 LIMIT 5;
```

**SQL-4 趋势（按自然日补 0）**

```sql
SELECT DATE(o.pay_time)  AS date,
       COUNT(*)          AS orderCount,
       COALESCE(SUM(o.actual_price), 0) AS gmvYuan
  FROM litemall_order o
 WHERE o.deleted = 0
   AND o.order_status NOT IN (101, 103)
   AND o.pay_time >= #{start} AND o.pay_time < #{end}
 GROUP BY DATE(o.pay_time);
```

Java 侧按 §1.6 生成完整日期序列（1/7/30 天），未命中日期填 `{orderCount:"0", gmv:0}`。

**SQL-5 存量计数**

-- pendingAftersaleCount
SELECT COUNT(*) FROM litemall_aftersale WHERE deleted = 0 AND status IN (0,1,2,3);

#### 2.3.3 校验链（**顺序固定**，任一步失败立即返回，不得跳步）

| # | 校验 | 失败返回 |
|---|---|---|
| 0 | 登录态 | `401`（网关） |
| 1 | 参数：`star∈[1,5]`、`content` 有值时 ≤500、`picUrls` ≤6 | `400 PARAM_INVALID` |
| 2 | 调 `CN-IN-01`（§4.5）取订单行：**不传 `userId`**（拿全量行信息后本地比对，见下方说明） | `FeignException 404` ⇒ `404 RESOURCE_NOT_FOUND`（「订单行不存在」） |
| 3 | `orderGoods.userId == 当前 userId` | `403 NOT_ORDER_OWNER` |
| 4 | `orderGoods.orderId == 入参 orderId` | `400 PARAM_INVALID`（「订单行不属于该订单」） |
| 5 | `orderGoods.orderStatus == 301` | `400 ORDER_GOODS_NOT_RECEIVED` |
| 6 | 未评价：`orderGoods.comment == 0`（且 `orderGoods.commented != true`） | `409 COMMENT_ALREADY_EXISTS` |
| 7 | `orderGoods.refundStatus != 2`（未退款） | `400 ORDER_GOODS_REFUNDED` |
| 8 | 落库：`value_id = orderGoods.goodsId`（服务端值）、`type=0`、`order_id`、`order_goods_id`、`star`、`content`、`pic_urls`（JSON 串）、`has_picture`、`status=0`、`reply_time=null`、`deleted=0` | 唯一键 `uk_comment_order_goods` 撞键 ⇒ `409 COMMENT_ALREADY_EXISTS`（**不得 500**） |
| 9 | 事务提交后 → 调 `CN-IN-08`（§4.4） | 失败**不影响**评价成功（见 2.3.4） |

> 顺序与 08 CN-36 一致（②已收货 → ③未评价 → ④未退款），**不得调整**：
> - 已评价的行（无论是否退款）⇒ 命中 6 `409 COMMENT_ALREADY_EXISTS`（对用户最有信息量）；
> - 已退款且未评价的行 ⇒ 命中 7 `400 ORDER_GOODS_REFUNDED`（BR-CM-05）；
> - `refund_status=1`（部分退）**可以评价**（只有全退 `2` 才禁），与 BR-CM-05「已退款行不可评」的判定落在「退款完成」上保持一致。
>
> 步骤 2 不传 `userId` 的原因：`CN-IN-01` 传 `userId` 时归属不匹配按 `404` 返回（P-29），CI-36 需要区分「行不存在（404）」与「行存在但非本人（403 `NOT_ORDER_OWNER`）」，因此取全量行信息后本地比对。

#### 2.3.4 301 → 501 唯一写点（R1 §1.5 的 R2 落地口径）

**结论：goods 不写订单表；goods 在本地事务提交后调用 order 域 `CN-IN-08`，由 order 域执行 CAS 跃迁。全仓只有 `CN-IN-08` 写 `order_status=501`。**

跃迁三条件（全部满足才跃迁，**逐条落 SQL**）：

1. 当前 `order_status=301`（CAS）；
2. 该订单**所有未退款行都已评价**：`NOT EXISTS(og WHERE og.deleted=0 AND og.refund_status=0 AND og.comment=0)`（`comment > 0` 即已评价；`comment=-1` 超期不可评**不参与**该判据、保持 -1 不动）；
3. **不得因「所有行已退款」跃迁**：须再判 `EXISTS(og WHERE og.deleted=0 AND og.refund_status<>2)`。

三禁止（R1 §1.5，继续有效）：

- 禁止把 501 当「退款完成」；
- **禁止写 `end_time` / `close_type`**（这两列只属于关闭/取消语义）；
- 禁止定时任务/批量刷 501。

**失败补偿（冻结）**：

- goods 侧：`CN-IN-08` 调用**最多 2 次**（首次 + 立即重试 1 次，间隔 0）；两次都失败 ⇒ `WARN` + **`INCR admin:logerr:{yyyyMMdd}`（TTL 48h，best-effort）+ 进程内计数**，**仍返回 `200 {commentId, orderStatusUpdated:false}`**（需求：评价成功不受其他失败影响）。
  - **v9 修订（R2-00f，以实现为准）**：原口径写「写操作日志（`status=1`、`type=1`、`target_type=order`、`target_id=orderId`、`action="尝试完成订单"`）」，**实现改为不写 `litemall_log`**。理由两条：①本卡 **§1.7（`:173-177`）红线**规定 `litemall_log` **唯一写服务是 admin**，goods 跨服务写表会破坏该约束；②goods 是**同步 Feign 调用方**，调用失败时再写一次远程/跨表日志，会造出"失败补偿本身再失败"的第二层故障。
  - 改走**既有观测面**：与 admin 的 `LogErrorCounter` **共用同一 Redis key** `admin:logerr:{yyyyMMdd}`（TTL 48h）——正是 `CI-08` 出参 `data.logErrorCount` 的读源 ⇒ 后台工作台"日志异常"角标能直接看见这次失败，**无需新增字段、端点或表**。实现：`litemall-goods/src/main/java/com/litemall/support/GoodsLogErrorCounter.java`（`KEY_PREFIX = "admin:logerr:"`、`ZONE = Asia/Shanghai`、Redis 未装配/不可用 ⇒ 只记本地计数 + `WARN`，绝不影响评价主流程）。
  - **key 格式已在册**：`admin:logerr:{yyyyMMdd}` 由 `08` §6.10「计数读取」行与本卡 §0.5 **P-3**（`:62`）登记，本节只是**追加第二个写入方**，不新增 key、不新增码位/字段。
- 残留风险（登记 D-40）：极端失败下订单停留 301（「已完成」晚到）。**不做定时批量修复**（R1 三禁止）；可由该订单后续任一行的再次评价触发（`CN-IN-08` 幂等）、或运维按日志重放 `CN-IN-08`。验收第 4/5 步不校验 501，正常网络下单次调用即成功。
- `CN-IN-08` 必须幂等：`og.comment` 已等于 `commentId` 时直接返回 `changed=false`；`order_status` 已 `≠301` 时返回 `changed=false`、`200`（**不报 409/500**）。

### 2.4 CI-54 · 领取优惠券 `POST /app/market/coupon/receive`（改契约）

**归属**：marketing 服务（`MarketingController.receiveCoupon` → `CouponServiceImpl.receiveCoupon`）；`/app/**`，`role=user`。

#### 2.4.1 入参 / 出参

入参（`CouponReceiveDTO`，与现状一致）：`couponId` 必填。

出参（`CouponReceiveResultVO`，**新增 `result`**）：

```json
{ "code": 400, "msg": "你已领过这张券", "data": {
  "result": "already_received", "message": "你已领过这张券" } }
```

```json
{ "code": 200, "msg": "领取成功", "data": {
  "result": "success", "message": "领取成功",
  "couponUser": { "id":"501", "couponId":"12", "name":"满 99 减 10",
                  "discount":10.00, "min":99.00, "endTime":"2026-11-30 23:59:59" } } }
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `data.result` | string | `success` / `already_received` / `sold_out` / `disabled`（**四态互斥**） |
| `data.message` | string | 与顶层 `msg` **同值** |
| `data.couponUser` | object \| 省略 | **仅 `success` 非空**；复用现状 `CouponUserVO{id,couponId,name,discount,min,endTime}`（`discount`/`min` 现状是元 `BigDecimal`，R2 **不改类型**，见 §5.5 例外） |

#### 2.4.2 四态映射表（**唯一判定顺序**，从上到下命中即返回）

| 序 | 条件 | code | `result` | `msg` = `data.message` |
|---|---|---|---|---|
| 1 | 未登录 | 401 | —（`data=null`） | 「请先登录」 |
| 2 | 券不存在 / 已逻辑删除 | 404 `RESOURCE_NOT_FOUND` | —（`data=null`） | 「优惠券不存在」 |
| 3 | 该用户已领过（`litemall_coupon_user` 存在该 `(coupon_id,user_id)` 行，**含已使用/已过期/已软删**） | 400 | `already_received` | **「你已领过这张券」** |
| 4 | 防刷：同用户同券 60s 内重复提交 | 400 | —（`data=null`） | 「领取过于频繁，请稍后再试」（**保持现状**，不属四态） |
| 5 | 券不可领：`status≠0`（已停用/已下架）或 `type≠0`（非主动领取）或 `time_type=1` 且当前不在 `[start_time,end_time]` | 400 | `disabled` | 「该券已停用」/「该券不在有效期」 |
| 6 | 已领完（`total>0` 且已发放数 `≥ total`） | 400 | `sold_out` | **「已领完」** |
| 7 | 其余 | 200 | `success` | 「领取成功」 |

> 【裁定】**失败态保持 `code≠200`**（03 §5.2「旧 `code/msg` 保留」），四态靠 `data.result` + `msg` 区分；`data` 形态例外见 §1.1 E-1。**不采用「全部 200」方案**（会破坏 06「前端只判 code」与 03 记账）。
> 【裁定】判定顺序 **already_received 先于 sold_out**：一人一券是用户维度的确定事实，需求 BR-CP-02 明确「不得与『已领完』混用」，已领过的用户在券领完后仍应看到「你已领过这张券」。

#### 2.4.3 并发与幂等（禁止 500）

- **撞唯一键** `uk_coupon_user(coupon_id,user_id)`（`DuplicateKeyException`）⇒ 捕获后转 `already_received`，**不得 500**。
- **最后 1 张只成功 1 人**：库存预减沿用 Redis `STOCK_KEY:{couponId}`；**新增 DB 复核**：`coupon_user` 落库后统计 `COUNT(*) WHERE coupon_id=? AND deleted=0`，若 `> total` ⇒ **软删本次发放行** + 返回 `sold_out`（不超额留账）。不加 `used` 列（0 DDL）。
- 幂等：同请求重放（用户已领到）走序 3 ⇒ `already_received`。
- `sold_out` 与 `disabled` 判定需读 `litemall_coupon` 最新值，不得用缓存快照。

#### 2.4.4 错误码汇总

`200 success` / `400`（`PARAM_INVALID`：couponId 缺失；`already_received`/`sold_out`/`disabled`/频控）/ `401` / `404 RESOURCE_NOT_FOUND` / `500`。`429` 保留但 R2 不用。

- **鉴权**：`X-Internal-Token`；无用户身份。
- **入参**：路径 `orderId` + body `{ "orderGoodsId":"8101", "commentId":"9001" }`（均为必填，字符串化 ID）。**（v8 修订确认，R2-00d）** 本行是**唯一正解**，来源 R2 实现；`07` §6.8 原写"仅路径 `orderId`、无 body"属契约错误，已于 `07` v8 同步纠正。**不得再改回"无 body"**——body 的两字段承载"置 `order_goods.comment = commentId`"这一步（幂等闸门：只有 `comment = 0` 的行会被标记，重复调用 `affected = 0` 不覆盖已有评价），缺了它 §2.3.4 的 ② 号跃迁条件（"不存在 `comment = 0` 的行"）永不满足 ⇒ 订单 301→501 **永不收敛**。
- **出参**（裸 DTO `OrderTryCompleteResultDTO`）：

```json
{ "orderId":"8001", "orderStatus":501, "changed":true }
```

- **逻辑（单本地事务）**：

```sql
-- ① 标记订单行已评价（幂等闸门：comment=0 才写）
UPDATE litemall_order_goods
   SET comment = #{commentId}, update_time = NOW()
 WHERE id = #{orderGoodsId} AND order_id = #{orderId}
   AND deleted = 0 AND comment = 0;
-- ② 尝试跃迁 301 → 501（三条件，见 §2.3.4）
UPDATE litemall_order o
   SET o.order_status = 501, o.update_time = NOW()
 WHERE o.id = #{orderId} AND o.deleted = 0 AND o.order_status = 301
   AND EXISTS     (SELECT 1 FROM litemall_order_goods og
                    WHERE og.order_id = o.id AND og.deleted = 0 AND og.refund_status <> 2)
   AND NOT EXISTS (SELECT 1 FROM litemall_order_goods og
                    WHERE og.order_id = o.id AND og.deleted = 0
                      AND og.refund_status = 0 AND og.comment = 0);
```

- `① affected=0`（已标记过）⇒ 仍执行 ②（可能上次 ② 失败），返回 `changed = (② affected=1)`。
- `② affected=0` ⇒ `changed=false`，`orderStatus` 回读当前值，**`200` 返回**（幂等，不报错）。
- **禁止**写 `end_time`/`close_type`；**禁止**由定时任务/批量任务调用。
- 错误码：`400 PARAM_INVALID`（`orderGoodsId`/`commentId` 缺失或非数字）、`404 RESOURCE_NOT_FOUND`（订单或订单行不存在/不属于该订单）、`500`。

## 5. 边界与陷阱（逐条：现象 → 原因 → 冻结口径）

### 5.1 删除仍有商品的分类必须 409 且提示「请先移走商品」

- 现象：后台点删除，期待"拒绝 + 明确提示"，验收第 8 步逐字判定。
- 原因：需求 BR-CAT-02 要求；DB 无外键（37 张表 `FOREIGN KEY` 0 处），必须应用层查。
- 口径：`409` + `data={"errorCode":"CATEGORY_IN_USE"}` + `msg="请先移走商品"`；检查范围 = **自身 + 子分类**，且**含已下架商品**（`status=2` 也算"仍有商品"），只排除 `deleted=1`。品牌同理 `BRAND_IN_USE`。

### 5.2 唯一键重复的错误映射（禁止先查后插、禁止 500）

| 唯一键 | 撞键 ⇒ | 陷阱 |
|---|---|---|
| `uk_category_name(pid,name)` | `409 CATEGORY_NAME_DUPLICATED` | 只捕获 `DuplicateKeyException` 后转；**不要**先 `SELECT` 再 `INSERT`（并发穿透）。注意：**根分类 `pid="0"`**（不是 `null`），否则 `(NULL,'服饰')` 与 `(NULL,'服饰')` 在 MySQL 唯一键下**不冲突**（NULL 不参与唯一性），会插出同名根分类 |
| `uk_brand_name(name)` | `409 BRAND_NAME_DUPLICATED` | 同上 |
| `uk_comment_order_goods(order_goods_id)` | `409 COMMENT_ALREADY_EXISTS` | CI-36 的幂等靠它，**不得**把 `DuplicateKeyException` 变成 500 |
| `uk_coupon_user(coupon_id,user_id)` | `400 already_received` | CI-54，**不得 500**（§2.4.3） |
| `uk_admin_username(username)` | `409 ADMIN_USERNAME_DUPLICATED` | CI-02 现状是「先查后插 + `Result.error`（code 500）」⇒ R2 必须改为唯一键兜底 + 409 |

### 5.3 分类/品牌删除 = **物理 `DELETE`**（【裁定】，改 08 CN-24/CN-28 的「逻辑删除」）

- 原因：`uk_category_name(pid,name)`、`uk_brand_name(name)` **不含 `deleted`**（实测 `03-add-keys.sql:23-24`）。软删后同 (pid,name) 再创建 ⇒ **永久 409**，验收脚本第 1/8 步重跑必卡死（运营不可自愈）。
- 依据：BR-CAT-02 已保证删除时无任何商品引用；BR-CAT-05（删除不影响历史订单）由订单行快照（`goods_name`/`order_goods` 已存）满足，不依赖分类行存在。
- 口径：`DELETE FROM litemall_category WHERE id=?`（先做 §3.4 三项检查，同事务）；品牌同。
- 回退方案（若产品坚持软删）：加迁移把 `uk_category_name/uk_brand_name` 改为 `(pid,name,deleted)`——**本期不做**。
- **对比：后台账号保持逻辑删除**（`uk_admin_username` 同样不含 `deleted`）：账号是低频对象，且 `log.admin`/`notice.admin_id`/`aftersale.audit_admin` 依赖账号行做历史审计；若需复名，运营应"启用"而非"删除"。**登记 D-39**。

### 5.4 两级分类约束

- 建：`pid=0` ⇒ `level="1"`；`pid≠0` ⇒ 父级必须 `level="1"`，本节点 `level="2"`；**三级直接 `400 PARAM_INVALID` + 「分类最多两级」**（不返回 `CATEGORY_LEVEL_EXCEEDED`，§1.2）。
- 改：**`pid` 不允许修改**（§3.3），从根上消除"改父级造三级/环"。
- 商品只能挂末级：`CI-10` 建品时 `categoryId` 必须存在且为末级（R1 已冻结，R2 不改）。

### 5.5 金额一律整数分

- 出参：`gmv`/`avgOrderValue`/`refundAmount`/`floorPrice`/`amount`（top5）全部**分**。
- 入参：`floorPrice` 为分；库 `DECIMAL(10,2)` 元 ⇒ 落库 `movePointLeft(2)`、出参 `movePointRight(2)`。**换算只允许在服务边界发生一次**。
- 已知例外（不改，登记）：`CouponUserVO.discount`/`min` 现状是**元** `BigDecimal`，CI-54 复用该 VO ⇒ **R2 不改其单位**（06 §7 禁止改类型/语义），前端按现状消费。
- `avgOrderValue` 用**整数除法向下取整**（先算分再除），禁止先算元再乘 100（会产生浮点误差与 ±1 分偏差）。
- `refundRate` 用 4 位小数 `HALF_UP`；**不得**用浮点 `double` 直接做展示值（用 `BigDecimal`，出参 JSON number）。

### 5.6 ID 一律字符串化

- 所有出参 ID（含 `PageVO` 内元素、`targetId`、`pid="0"`）为字符串；对内裸 DTO 可用 `Long`（§2.2 说明），**对外必须字符串**。
- 前端入参字符串数字可被 `Long` 接收（Jackson 默认支持），但**不得**把 `id` 声明成 `String` 再 `Long.parseLong` 裸解析（异常变 500）——统一用 `Long` 字段 + `@Valid`。

### 5.7 隐藏评价后 C 端评价数 -1（验收第 5 步）

- **唯一口径**：C 端评价数 = `COUNT(*) FROM litemall_comment WHERE value_id=? AND type=0 AND status=0 AND deleted=0`（**只统计 `status=0`**）。
- 落点（两处，必须同口径、实时派生、不缓存）：
  1. `CI-32 GET /app/goods/detail` 的 `commentCount` —— 语义收窄为"未隐藏评价数"（08 §1.2 已裁定）。
  2. `CI-35 GET /app/goods/comment/list` 的 `total` —— 同样只计 `status=0`。
- 因此：发表评价（`status=0`）⇒ +1；`CN-31` 隐藏（`status=1`）⇒ -1；恢复 ⇒ +1。**不需要**任何计数器列或缓存失效动作。
- 后台列表 `CN-29` 的 `total` **包含**已隐藏项（后台要看得到），二者口径不同，**不得复用同一 SQL**。

### 5.8 评价的幂等与唯一性

- 「未评价」判据：`order_goods.comment == 0`（`-1` 超期不可评、`>0` 已评价）。
- 幂等最终靠 `uk_comment_order_goods(order_goods_id)`；预检查只用 `CN-IN-01` 返回的 `commented/commentId`（降低无效插入），**不得**用"先查 comment 表再插入"作为唯一保障。
- 一笔订单多行：每行 1 条评价；`comment=-1` 的行不参与 501 判定（不阻塞"全部已评价"）。

### 5.9 501 写点唯一 + 三禁止（§2.3.4 已详述）

- 全仓**唯一**写 `order_status=501` 的地方 = `CN-IN-08`。
- 禁写 `end_time`/`close_type`（关闭语义专用）；禁止定时/批量刷 501；禁止把 501 当"退款完成"。
- 已 501 的订单仍可 7 天内申请售后，售后**不改主状态**、501 不回退（R1 §1.5）。

### 5.10 券：并发、唯一键、四态不混用

- `already_received` 与 `sold_out` **不得混用**（BR-CP-02），判定顺序见 §2.4.2。
- 最后 1 张：Redis 预减 + DB 落库后复核（§2.4.3），不超额留账、不 500。
- 有领取记录的券**只能停用不能删除**（BR-CP-10，R1 已由 `COUPON_IN_USE` 保证，R2 不改）。

### 5.11 日志：写入不阻断业务，异常要可数

- 后台写动作（商品上下架、库存调整、券发放/停用、内容停用、评价回复/隐藏、账号启停、发货、物流单号修改、退款、售后同意/驳回/跳过收货、立即关单）**必须写日志**；写失败只 `WARN` + `INCR admin:logerr:{yyyyMMdd}`，**不抛异常**。
- `target_type` 必须落在 §2.5.1 白名单内（否则 CI-13 筛不出来 = 审计缺口）。
- `log.type`/`log.status` 字典冻结见 §1.5.1（D-36 收口）；出参 `typeText`/`statusText` 同步。
- **不提供 `adminId` 筛选**（表无列，§2.5.1 裁定）。

### 5.12 后台会话失效（`auth:ver`）三处 + 不新增 logout

- 仅在 ①修改密码 ②重置密码（CI-04）③账号被禁用（CN-37）三处 `INCR auth:ver:{adminId}`。
- 登录成功时把当前 `ver` 写进 token；`AdminAuthFilter` 比对，不一致 ⇒ `401`。
- **不新增** `POST /admin/auth/logout`（06 §2）。**当前代码尚无该机制（P-1），R2 必须补**。

### 5.13 公告：无 `sort_order`、停用即消失

- 库无 `sort_order` 列 ⇒ `sortOrder` **不提供**（入参/出参都不加），排序固定 `add_time DESC`；这是对 08 CN-34/35/36 的显式裁剪（回写 08）。
- `enabled=false` ⇒ C 端 `CI-59` 立即不可见；`enabled=true` ⇒ 恢复（BR-CMS-04）。`CI-59` 只返回 `enabled=1`。
- 公告不提供删除（08 已定）；停用必须写日志（§5.11）。

### 5.14 账号：不能删除/禁用自己；禁用后不能登录

- CN-37：`id==当前 adminId && status==0` ⇒ `403 ADMIN_SELF_FORBIDDEN`（CI-05 删除同理）。
- 登录（CI-06）：`status=0` ⇒ `403 ADMIN_DISABLED`；密码错/用户名不存在统一 `401 LOGIN_FAILED`（不区分，防枚举）。
- 禁用后旧 token 立即失效（§5.12）。

### 5.15 分页稳定与筛选保持

- 所有分页 SQL 必须有确定次序键（见 §1.4）；`CI-31` 即使不传 `sort` 也用 `id DESC` 兜底，保证 BR-SEARCH-06「翻页保持」。
- 前端（mobile-web）负责把筛选条件写进 URL query；后端**不得**依赖 session 保存筛选态。
- `CI-31` 的 `minP>maxP` 自动交换（BR-SEARCH-05），不报 400。

### 5.16 C 端分类隐藏空分类（CI-33 不改契约）

- `CI-33 GET /app/goods/category` 保留出参形状，但**过滤收紧**：只返回"自身或任一子分类下存在 `status=1`（在售）商品"的分类；空分类 C 端隐藏、后台（CN-21）可见（需求 §5.2 末段）。
- 这是**过滤规则**不是字段变化，属"保留"。

### 5.17 报表现已存在字段的兼容

- `CI-08` 沿用 `goodsTotal`/`userTotal`/`todayOrders`/`undelivered`，字段名与语义不变（`todayOrders` 恒今日）；新增字段只增。
- `unavailable[]` 与「`—` 展示」是**前端**契约：后端只给 `null` + 字段名，前端渲染 `—` 并标"暂不可用"；后端**不得**返回 `0` 或 `NaN` 冒充。

### 5.18 跨域只读 join 的白名单（同库允许，写禁止）

- 允许的只读 join：goods 读 `litemall_goods`/`litemall_order`/`litemall_order_goods`/`litemall_user`（CN-29）；order 读 `litemall_refund`（报表、售后退款单号，R1 先例）；admin 读自身表 + 经 Feign 取各域统计。
- 禁止：goods 写 `litemall_order*`；admin 直连 goods/marketing 表写；marketing 写 `litemall_admin`。

### 5.19 对内 404/409 必须被 admin 正确转译

- Feign 对内非 200 ⇒ `FeignException`；admin 必须按状态码映射：`404 → Result(404, RESOURCE_NOT_FOUND)`、`409 → Result(409, 原 errorCode 由 body 解析或按端点固定)`、`400 → Result(400, PARAM_INVALID)`。
- **不得**把 `FeignException` 直接冒泡成 `500`（会让"分类不存在"变成"服务器错误"，验收判不通过）。
- 建议：goods/marketing 对内异常体也带 `{"errorCode":"…"}`（裸返回不套 `Result`，但异常体可带），admin 解析同名 `errorCode` 透传，实现"对外/对内同码"。

### 5.20 分类树缓存 `category:tree` 的失效时机（R2-11 追加 · 实现约束）

- **现象**：后台新建/编辑/删除分类后，C 端 `CI-33` 分类树最长 5 分钟才更新；验收第 1 步「后台新建分类 ⇒ 前台可见」**偶发**不过（不是每次都不过，所以容易被当成环境问题）。
- **原因（为什么禁止在事务体内失效）**：`del` 本身只是"下次读重建"的信号。若在 `@Transactional` 方法**体内**就 `del`，此时事务尚未提交；紧接着的并发读者（另一请求/另一连接）发现缓存缺失 ⇒ 立刻重新 `SELECT` 分类树。MySQL InnoDB 默认 **REPEATABLE READ** 下该读者的一致性快照只包含**提交前**的数据 ⇒ 读到的还是旧树，并把它写回 `category:tree`、带上 300s TTL。结果：失效动作反而完成了一次"旧快照预热"，前台 5 分钟看不到新分类。
- **冻结口径**：
  1. `category:tree` 的失效**必须挂在事务提交之后**：`TransactionSynchronization#afterCommit`（R2 实装已在 `CategoryServiceImpl` 落地；等价写法 `TransactionSynchronizationManager.registerSynchronization` / `@TransactionalEventListener(phase = AFTER_COMMIT)`）。**禁止**在 `@Transactional` 方法体内直接 `cacheService.del("category:tree")`。
  2. `afterCommit` 阶段抛出的异常**不得**回滚业务（事务已提交）：失效失败只 `WARN`，不得向上抛。
  3. **无事务上下文**（只读路径、单测直调 service）时 `afterCommit` 不会触发 ⇒ 必须有"无事务则立即 `del`"的兜底分支，否则缓存不失效、单测假通过。
  4. **一致性窗口**：commit 到 `del` 完成之间是微秒级，**不是**用户可见窗口；真正的陈旧窗口只来自 TTL 300s，即**失效事件本身丢失**（Redis 抖动 / 进程在 commit 与 del 之间崩溃）时的降级上界。该降级可接受，**不为此引入 MQ / 事务消息**；验收判据按"正常路径秒级可见"。
  5. 失效的**唯一写侧**是 goods 的 `CN-21`/`CN-23`/`CN-24`；`CI-33` 是纯读端，不得在读路径里"重建后再 `del`"（会造成无谓抖动）。
- **为什么写进卡而不是只写代码注释**：这条口径跨端点（写侧 `CN-21~24` + 读侧 `CI-33`）且跨事务边界，只写在某个 service 里会被下一个改这块实现的人忽略；`08` v11 §1.3 同步登记了读端视角。
